# CH2 Macro AI 어시스턴트 리뷰

검토일: 2026-11-07. 대상은 현재 로컬 작업 트리의 제품 AI와 각 앱의 화면 연결이다. 운영 서버의 배포본을 감사한 결과는 아니다. 제품 코드와 정책은 수정하지 않았다.

## 판단

실제 관측값을 참조로 검증하는 방향은 적절하지만, 현재 구현을 모든 화면을 이해하는 출시용 어시스턴트로 보기에는 중요한 연결·검증 누락이 있다. 모델 교체보다 화면별 입력 계약과 응답 검증을 먼저 고치는 것이 필요하다.

현재 `/api/ai/chat`은 `orchestrator.handle_chat`에서 `dialogue.answer_land`로 직접 연결된다. 함수 이름과 달리 모든 제품 앱이 이 경로를 공유한다. 기존 번들·open mode·Explain 관련 코드가 존재한다고 해서 현재 채팅에 자동으로 적용되지는 않는다.

우선순위: P1은 출시 전에 우선 수정할 문제, P2는 해당 기능의 정확성·운영 안정성을 위해 보완할 문제다.

## 1. [P1] 일반 지식 분류로 실제 관측값 검증을 우회할 수 있음

위치: `backend/app/ai/dialogue.py:721`, `:923`.

숫자와 참조를 엄격히 검증하는 분기는 모델이 `kind="screen"`으로 분류한 답변에만 적용된다. `kind="knowledge"`이고 참조가 없으면 실제 현재 화면에 관한 주장을 포함해도 통과한다. 모델의 분류 오류만으로 발생하며 악의적 사용자 입력이 필수인 것은 아니다.

오프라인 재현:

- 실제 입력: 표본 120건, 조정 R² 0.5.
- 모델 응답을 모의 입력: `kind="knowledge"`, “현재 지역 A의 분석 표본은 98765건이고 조정 R²는 0.999입니다.”
- `_render`뿐 아니라 전체 `answer_land` 호출에서도 그대로 반환됨.
- `llm_used=true`, 근거는 “CH2 제품 지식 및 일반 통계”로 표시됨.

이는 실제 모델이 그 문장을 생성했다는 관측이 아니라, 그러한 모델 출력이 나올 경우 서버가 차단하지 못한다는 재현이다.

개선: 일반 지식의 가상 숫자·수식은 허용하되 현재 지역·화면에 대한 관측 주장은 분류값과 무관하게 검증한다. 관측 주장과 일반 설명을 응답 스키마에서 구분하고, 관측에는 서버가 확인할 수 있는 근거 참조를 요구한다.

## 2. [P1] Insight와 집합 기본목록의 자료가 현재 채팅 근거로 변환되지 않음

위치: `backend/app/ai/dialogue.py:82`, `frontend-insight/src/pages/Insight02.tsx:133`, `frontend-collective/src/api/aiContext.ts:45`.

`_screen`에 Insight 계열, `BuildingList`, `CommercialList` 처리가 없다. 화면에서 보내는 자료가 있어도 모델에 전달되는 관측 근거는 0개다. 세 패널 모두 합성 입력으로 빈 근거 목록을 재현했다.

Insight의 공개 3번 페이지는 내부적으로 `Insight02`이다. 프론트는 상관계수·표본 수와 `explain.title/summary`를 보내지만 현재 대화 경로는 이를 읽지 않는다. 보고서 전체 본문과 현재 선택한 그래프 상태도 완전하게 전달하지 않는다.

현재 브라우저의 “항목별 수치가 없습니다”라는 답변과 일치한다. 보고서가 화면에 있다는 사실만으로 AI가 화면이나 DOM을 직접 읽는 구조는 아니다.

개선: 제품에서 사용하는 모든 패널을 등록한 입력 계약을 만들고, 목록·보고서용 변환기를 구현한다. 보고서는 제목·기준기간·방법·결과·한계를 전달하고, 표 수치는 구조화된 참조로 별도 제공한다. 지원하지 않는 패널은 일반적인 화면 설명을 만들어내지 말고 지원 범위를 명시한다.

## 3. [P1] 공통 화면 등록 effect가 자기 자신을 반복 갱신할 수 있음

위치: `shared/ai-assistant/ActiveAiView.tsx:101`, `:105`, `:124`.

`PublishAiContext`의 effect는 전체 `api` 객체에 의존한다. `upsert`가 `layers`를 바꾸면 공급자의 `context/value`와 `api` 객체가 바뀐다. 그러면 effect cleanup이 `remove`를 실행하고 다시 등록한다. `remove`는 매번 새 배열로 상태를 갱신해 이 순환을 유지할 수 있다. `upsert` 내부의 동일값 비교만으로는 cleanup의 삭제를 막지 못한다.

영향: 반복 렌더링, 화면 문맥의 삭제·재등록, 불필요한 CPU 사용과 불안정한 문맥 갱신. 이는 정적 코드 분석으로 확인한 문제이며, 이번 검토의 브라우저 로그 조회에서는 해당 경고를 새로 포착하지 못했다.

개선: effect 의존성을 안정적인 `upsert/remove` 함수와 실제 `context`로 좁히고, 존재하지 않는 항목 삭제는 상태를 변경하지 않게 한다. 마운트·문맥 변경·언마운트의 등록 횟수를 검증한다.

## 4. [P2] 지역프로필의 주요 지표가 AI에 전달되지 않음

위치: `frontend-profile/src/App.tsx:192`, `backend/app/ai/dialogue.py:640`.

프론트는 버전·기준월·기간·행정 단위·대표 유형·총 거래건수만 보낸다. 화면에 있는 거래금액, 인구, 순위, 유형별 구성, 토지 통계, 아파트 분위와 쌍둥이 지역은 빠져 있다. 서버 처리도 사실상 거래건수와 기간만 수치 근거로 만든다.

재현: 거래금액·인구·순위를 포함한 합성 입력도 현재 변환기는 “3년 거래 1234건”, “롤링 구간 3년” 두 항목만 남긴다. 프로필은 완료 달력 연도를 쓰므로 ‘롤링 구간’이라는 라벨도 부적절하다.

개선: 현재 표시된 프로필의 집계기간과 주요 카드의 값을 전달하고, 각 값의 단위·표본·해석 한계를 함께 매핑한다. 거래액 합계와 지역 전체 자산가치를 구분하는 최근 도움말 설명도 AI 지식과 맞춘다.

## 5. [P2] 주거 임대 상세를 열어도 AI는 기본목록의 문맥을 사용함

위치: `frontend-rent/src/App.tsx:255`, `frontend-rent/src/components/BuildingDetailModal.tsx:213`.

임대 앱은 목록 전환율을 등록하지만 주거 건물 상세에는 화면 문맥을 등록하는 코드가 없다. 사용자가 건물의 전환율·선택 건물 평균·롤링 그래프·거래목록을 보고 질문해도 그 상세값이 AI 입력으로 교체되지 않는다.

상세에 표시된 값을 해석할 수 없거나, 지역 전환율을 개별 건물 전환율처럼 혼동할 위험이 있다. 상세 회귀 탭은 현재 비활성 상태이며 이 지적은 활성화된 상세 기능에 대해서도 해당한다.

개선: 활성 상세 탭별로 건물 식별·자료기간·선택 지표·지역/건물/비교대상 평균을 구분한 문맥을 등록하고, 상세를 닫으면 기본목록 문맥으로 복귀시킨다. 원시 거래 행을 외부 모델에 전송할 필요는 없다.

## 6. [P2] 상업 임대통계의 건물유형을 연도처럼 처리하며 일부 자료를 누락함

위치: `backend/app/ai/dialogue.py:627`, `frontend-rent/src/api/aiContext.ts:129`.

프론트의 `annual` 구조는 `지표 → 건물유형 → 값`이다. 서버는 안쪽 키를 `year`로 취급해 정렬 후 마지막 4개만 읽는다. 실제 건물유형이 5개인 입력에서 1개가 탈락하며, 지표도 앞 12개만 처리한다. 지표명과 단위도 사용자가 읽는 라벨로 변환하지 않는다.

재현: office·mid_retail·small_retail·strata·retail_all에 값이 있는 입력에서 `mid_retail` 값이 빠지고 다른 네 값만 근거로 남았다.

개선: 연간 추세 자료와 현재 상권의 유형별 통계를 다른 스키마로 구분한다. 건물유형을 명시적으로 매핑하고 임대료·금액·구성비·수익률별 단위와 기준기간을 보존한다. 임의의 ‘마지막 4개’ 제한은 사용하지 않는다.

## 7. [P2] AI 세션이 로그인 사용자와 연결되지 않음

위치: `backend/app/ai/sessions.py:71`, `backend/app/ai/orchestrator.py:1368`.

구독 게이트는 요청자의 접근 가능 여부를 확인하지만, AI 세션 조회는 클라이언트가 보낸 `session_id`만 사용한다. 세션 저장소에는 사용자 소유권이 없다. 따라서 세션 ID가 알려지면 다른 접근 허용 사용자도 같은 대화·직전 근거 객체를 참조할 수 있는 구조다.

오프라인 재현: 동일 ID로 조회하면 동일한 가변 세션 객체가 반환됨. 실제 다른 계정이나 운영 사용자 자료에는 접근하지 않았다. UUID를 무작위로 추측할 수 있다는 주장이 아니라 소유권 검증 부재에 대한 지적이다.

개선: 로그인 사용자 ID와 세션을 묶고 매 요청 소유권을 검증한다. 대화 턴 수·본문 크기도 상한을 둔다. 현재는 TTL이 있어도 활성 세션의 `turns`는 계속 증가한다. 실제 운영 계정 간 격리 검증은 별도로 필요하다.

## 8. [P2] Insight 제품 지식의 번호·내용이 실제 화면과 다름

위치: `backend/app/ai/knowledge/product.py:199`, `frontend-insight/src/App.tsx:60`.

제품 지식은 1번 금리·유동성, 2번 유형 상관관계, 3번 연립 층별효용 등 예전 5개 구성으로 설명한다. 현재 화면은 1번 경제지표, 2번 금리·유동성, 3번 유형 상관관계 등 13개 주제다. 화면 자료 연결을 고친 뒤에도 잘못된 보고서·경로를 안내할 수 있다.

개선: 공개 번호·내부 ID·제목·방법·제한사항을 한 카탈로그에서 관리하고 UI와 AI 지식을 같이 생성한다. 보고서 제목으로 질문했을 때 다른 보고서 내용을 답하지 않는 검증을 추가한다.

## 9. [P2] 실패 사유를 구분하지 않아 재시도로 해결되지 않는 문제를 숨김

위치: `backend/app/ai/llm.py:207`, `backend/app/ai/dialogue.py:1009`.

외부 모델의 통신·시간 초과·응답 오류와 답변 근거 검증 실패가 최종적으로 유사한 “잠시 뒤 다시 질문” 안내로 모인다. 화면 자료 연결 누락처럼 반복해도 해결되지 않는 문제를 사용자에게 일시 장애처럼 보이게 한다.

현재 브라우저에서도 이 문구를 확인했다. 그 개별 응답이 통신 실패인지 검증 실패인지는 해당 호출의 서버 로그 없이 단정하지 않았다.

개선: 입력 자료 부족, 지원하지 않는 패널, 외부 모델 오류, 근거 검증 실패, 사용 한도 초과를 구분한 상태 코드를 반환한다. 사용자에게는 이해할 수 있는 안내를, 운영 로그에는 원인·추적 ID를 남기되 질문 원문과 비밀값은 불필요하게 저장하지 않는다.

## 확인한 장점과 범위

- 제품 API의 구독 게이트와 AI 요청 속도 제한이 존재한다. AI가 완전히 무인증으로 열려 있다는 결론은 아니다.
- `screen` 답변의 참조값·단위 검증과 원시 거래 행 제외 방향은 적절하다.
- 지역회귀와 단지 거래 회귀를 구분하는 전용 설명, 적용 전환율의 출처 설명이 존재한다.
- 월 사용량 기록과 호출·예산 제한이 구현되어 있다. 다만 실제 운영의 동시성·권한 설정·비용 정산까지 검증한 것은 아니다.
- 일반 지식의 가상 숫자와 실제 관측값을 구분해야 한다는 정책은 적절하다. 문제는 현재 분류 결과만으로 검증을 건너뛸 수 있다는 구현이다.

## 실제 수행한 검증

1. 기존 테스트 5개 파일 실행: `test_land_ai_dialogue.py`, `test_ai_gateway.py`, `test_ai_assistant_improvements.py`, `test_ai_usage.py`, `test_rent_conversion_ai.py`.
2. 결과: **120 passed**. 첫 실행의 사용량 테스트 2개는 임시 폴더 권한 오류로 실행되지 않았고, 저장소 안의 새 임시 경로를 지정한 재실행에서 모두 통과했다.
3. 별도 오프라인 검증: Insight·주거/비주거 기본목록의 빈 근거, 지역프로필의 수치 누락, 상권 건물유형 누락, 일반 지식 분류의 검증 우회, 세션 ID만으로 객체 재조회.
4. 현재 Insight 브라우저의 실제 질문·응답과 코드 경로를 대조했다. 반복 업데이트 관련 브라우저 로그 조회에는 새 오류가 없었다.
5. 로컬 AI health는 정상 응답하고 API 키가 설정된 상태임을 확인했다. API 키나 토큰 값은 출력하지 않았다.

추가 실제 LLM 호출, 운영 서버 변경, 실사용자 데이터 접근, 다른 계정의 세션 접근, 부하 테스트, 전체 앱의 모든 탭에 대한 실모델 E2E 검증은 수행하지 않았다. 120개 테스트 통과는 현재 전체 서비스의 답변 품질을 보장하지 않는다.

## 권장 수정 순서

1. 일반 지식 분류의 관측값 검증 우회와 공통 화면 등록 effect를 먼저 수정한다.
2. 화면별 전달 계약을 정리하고 Insight·집합 기본목록·지역프로필·임대 상세·상권 변환기를 보완한다.
3. Insight 보고서와 제품 지식을 동기화하고 실패 상태를 구분한다.
4. 계정별 세션 격리와 대화 저장 상한을 보완한다.
5. 대표 질문으로 실제 모델 E2E를 검증한다. 현재 화면 설명, 특정 수치 해석, 탭 변경 후 질문, 직전 결과 비교, 일반 통계 질문, 자료 없는 질문을 포함한다.

기존 회귀·집계 엔진은 이번 수정의 중심이 아니다. 우선 AI가 현재 화면의 올바른 근거를 받도록 만들고, 그 근거를 벗어난 관측 주장을 걸러야 한다.
