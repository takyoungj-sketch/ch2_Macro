# 복합 거래 목록 — 간이 토지배분단가 오류 검토

검토일: 2026-11-03 (KST)

대상: 현재 로컬 작업 트리의 거래목록 모달, 배분 가정 입력창, 신축원가표, 계산 유틸리티 및 거래 API의 연식 필드 연결. 미커밋 구현을 포함한다. 운영 배포본과 실제 브라우저 화면은 검증하지 않았다. 애플리케이션 코드는 변경하지 않았다.

## 정상 동작 확인

- 계산 단위는 거래금액 만원, 면적 ㎡, 신축원가 만원/㎡로 일치한다.
- 식은 `(거래금액 − 연면적 × 신축원가 × 잔가율) / 대지면적`이다. 원가 상한을 토지단가 하한으로 사용하는 범위 방향도 맞다.
- 구조가 없을 때 같은 용도의 원가 범위를 넓혀 쓰는 동작, 음수 토지단가 표시, CSV에서 배분 결과를 제외하는 동작은 도움말에 명시된 설계다.
- 신축원가 기본값은 임의 가정이라고 화면에 안내한다. 기본값의 시장 적정성은 이번 코드 검토 대상에 포함하지 않았다.

## 1. [P1] 사용승인연도만 있는 거래의 연식을 무시한다

근거: `frontend-built/src/utils/allocationCost.ts:55`, `:203`.

`allocationAge()`는 사용승인연도를 우선할 수 있지만, 앞선 `hasBuiltYear()` 검사는 건축연도 또는 원장 경과연수만 인정한다. 따라서 원장 연식이 결측이고 보강된 사용승인연도만 있으면 해당 함수를 호출하지 않고 최종잔가율 10%를 적용한다. API는 원장 `building_age`와 보강 `approve_year`를 별도로 반환하므로 가능한 입력 조합이다.

실행 재현: 단독·RC, 계약연도 2025, 사용승인연도 2020, 원장 연식 결측, 거래금액 50,000만원, 연면적·대지면적 각각 100㎡, 기본 원가 180~200만원/㎡, 내용연수 50년.

- 사용승인연도로 계산하면 경과 5년, 잔가율 90%, 토지단가 320~338만원/㎡, 기준값 329만원/㎡.
- 실제 결과는 연식 없음, 잔가율 10%, 토지단가 480~482만원/㎡, 기준값 481만원/㎡.

영향: 사용할 수 있는 연식이 있어도 건물가가 과소 차감되어 토지 배분단가가 높아진다.

권고: 연식 사용 가능 여부를 `allocationAge()`의 결과로 판단하고 상세 입력창에도 같은 판정을 사용한다.

## 2. [P2] 목록을 닫아도 배분 가정이 초기화되지 않는다

근거: `frontend-built/src/components/BuiltTransactionListModal.tsx:70`, `:75`; `frontend-built/src/App.tsx:1928`.

목록 컴포넌트는 부모에 계속 마운트된 상태로 `open`만 변경한다. 닫기 효과는 배분 모드와 하위 창만 닫고 `bands`, `rowOverrides`를 초기화하지 않는다. 조회 조건이 바뀌어도 두 상태는 유지된다.

재현 절차: 원가표 또는 특정 행의 원가를 변경 → 거래 목록 닫기 → 다시 열기 → 배분 버튼 켜기. 이전 수정값이 다시 적용된다.

영향: 도움말의 “이 조회를 닫으면 조정 내용은 사라집니다”와 실제 수명이 다르다. 새 조회에서도 이전 가정을 사용할 수 있다.

권고: 조회 세션의 경계를 정하고 닫기 또는 새 조회 시작 시 두 상태를 함께 초기화한다.

검증: 상태 수명 및 부모 렌더 구조를 코드로 확인했다. 브라우저 클릭 재현은 수행하지 않았다.

## 3. [P2] 입력 범위를 검증하지 않아 입력값과 적용값이 달라진다

근거: `frontend-built/src/components/AllocationUi.tsx:160`, `:177`, `:410`; `frontend-built/src/utils/allocationCost.ts:152`, `:209`.

숫자 여부만 검사하고 의미상 유효 범위를 검사하지 않는다. 원가 하한·상한은 역전 시 조용히 교환하고, 최소잔가는 0~100%로, 잔존연수는 0~내용연수로 계산 단계에서만 제한한다. 입력창에는 사용자가 넣은 숫자가 남는다. 원가표에서는 빈 문자열도 `Number("") === 0`으로 저장한다.

실행 재현:

- 내용연수 50년인 행에 잔존연수 100년을 입력하면 저장값은 100이지만 계산에는 50년, 잔가율 100%가 적용된다.
- 원가를 -200~-100으로 입력하면 `allocateRow()`는 성공(`ok: true`)을 반환하지만 단가 세 값은 모두 `null`이 되어 화면에는 “부적합”이 표시된다. 잘못된 원가 입력이라는 원인 안내는 없다.

영향: 사용자가 확인한 입력 숫자와 실제 산출에 사용한 가정을 일치시키기 어렵다. 원가표의 잘못된 입력은 같은 용도의 여러 행에 영향을 준다.

권고: 유효 범위를 입력 시 명시적으로 검증하고, 보정한다면 입력창에도 적용값을 반영한다. 원가표는 빈칸 편집 상태와 숫자 0을 구분한다.

## 4. [P2] 잔존연수를 지우면 입력창은 비지만 자동 계산값은 적용된다

근거: `frontend-built/src/components/AllocationUi.tsx:135`, `:157`, `:177`, `:256`.

초기 입력값 동기화 효과는 `row.id`, `overrideEmpty`, `bands`만 감시한다. 다른 행별 수정값이 남은 상태에서 잔존연수만 지우면 `overrideEmpty`가 바뀌지 않아, 자동 잔존연수가 입력창에 다시 표시되지 않는다.

실행 재현: 경과 5년인 행에서 내용연수를 60년으로 변경 → 잔존연수를 10년으로 변경 → 잔존연수 입력을 삭제.

- 입력창 값: 빈 문자열.
- 남은 개별 가정: `{ life: 60 }`.
- 실제 계산 잔존연수: 55년.

영향: 같은 창에서 입력칸과 결과 설명이 서로 다른 상태를 보여준다.

권고: 자동값 복귀 동작을 입력창에 반영하거나, 자동 계산값을 placeholder/별도 표시로 명확히 보여준다.

검증: TypeScript를 변환해 실행하고 React 상태·효과의 최소 모사로 입력 콜백과 동기화 경로를 재현했다. 실제 DOM 테스트는 아니다.

## 5. [P2] 원가표 변경으로 결과가 달라져도 목록에서 수정 표시가 없다

근거: `frontend-built/src/utils/allocationCost.ts:138`; `frontend-built/src/components/AllocationUi.tsx:46`.

수정 여부 `customized`는 개별 행 override만 검사한다. 공통 원가표에서 기준을 변경해도 해당 값을 사용하는 행은 수정되지 않은 색으로 표시된다. 원가표 자체에는 변경 배경 표시가 있으나 거래목록에는 전달되지 않는다.

실행 재현: 단독·RC 원가를 기본 180~200에서 100~120으로 변경. 위 경과 5년 예시의 기준 토지단가는 329에서 401만원/㎡로 바뀌지만 `customized`는 계속 `false`다.

영향: “노란 글씨는 이 조회에서 바꾼 값”이라는 안내만으로는 기본 가정과 수정 가정을 구분할 수 없다.

권고: 공통 원가표 변경과 개별 행 변경을 모두 표시 판정에 포함하고 출처를 툴팁에 구분한다.

## 검증 범위와 우선순위

계산 유틸리티는 로컬 TypeScript를 JavaScript로 변환해 기본값·사용승인연도 결측 분기·음수 원가·잔존연수 상하한·공통 원가 변경을 실행했다. 입력 동기화는 최소 상태 모사로 확인했다. 운영 DB에서 발생 건수나 영향 규모는 집계하지 않았다.

수정 순서는 1번 연식 판정 → 2번 가정 수명 → 3번 입력 검증 → 4번 입력 동기화 → 5번 수정 표시를 권한다.
