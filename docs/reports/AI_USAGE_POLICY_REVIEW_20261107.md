# CH2 Macro AI 사용량 제한 정책 리뷰

검토일: 2026-11-07. 운영 VPS의 실행 중인 관리자 API, 운영 설정, 로컬 관리자 API, 사용량 장부 및 현행 로컬 수정본을 대조했다. 설정·정책 변경이나 배포는 하지 않았다.

## 현재 실제 정책

- 적용 범위: 사용자 개인이 아닌 서버 전체. Macro 구독에 따른 접근 가능 여부는 별도의 제품 게이트가 검사한다.
- 월 한도: 모델 호출 200회 또는 자체 추정 비용 10,000원 중 하나라도 도달하면 이후 모델 호출을 중지한다.
- 경고: 호출 또는 비용이 한도의 80%에 도달하면 관리자 집계에 경고 상태가 생긴다.
- 단기 제한: IP 기준 분당 AI API 요청 30회. 모델 호출 수가 아니라 `/chat`, `/history`, `/explain`의 요청 제한이다. 메모리 기반이며 재시작하면 단기 제한 기록은 사라진다.
- 월 구분: UTC 달력 월. 한국 시간으로 매월 1일 오전 9시에 새 달 장부로 넘어간다.
- 환산: 설정 환율 1달러=1,400원과 코드의 모델별 토큰 단가로 원화를 추정한다. 공급자 청구서를 조회한 금액이 아니다.
- 저장: `logs/ai_usage/YYYY-MM.jsonl`의 호출별 이벤트. 파일이 보존되면 서버 재시작 후에도 월 사용량은 유지된다. 질문·답변 원문은 저장하지 않는다.
- 설정에서 월 횟수 또는 금액을 0으로 두면 해당 제한을 해제한다. 현재 두 제한은 모두 켜져 있다.

## 실행 중인 관리자 API 확인값

운영 2026년 11월: 모델 `gpt-5-mini`, 12회 / 200회, 추정 104.2원 / 10,000원. 경고·중지 상태 모두 false였다. 운영 설정을 읽은 결과와 실행 중인 관리자 API 값이 일치했다.

로컬 2026년 11월: 111회 / 200회, 추정 786.9원 / 10,000원. 운영과 별도 장부다. 로컬 장부와 로컬 관리자 API 값도 일치했다.

이 수치는 조회 당시 스냅샷이며 이후 호출로 바뀔 수 있다. 운영에는 직전 AI 수정 작업을 배포하지 않았으므로 신규 출처 검증 호출은 로컬에 먼저 적용된 상태다.

## 주요 판단

현재 정책은 개발·실험 비용을 보호하는 서버 전체 안전장치로는 이해할 수 있다. 그러나 정식 서비스에서 각 사용자의 사용 가능량을 공정하게 관리하는 정책은 아직 아니다.

### 1. 서버 전체 200회는 사용자별 이용권이 아니다

사용자 ID·요금제별 잔여량이 없다. 한 사용자의 집중 사용, 관리자 시험 또는 같은 `_openai_chat`을 사용하는 AI2·AI3 호출이 공통 한도를 소모해 다른 사용자가 함께 중지될 수 있다. 세션 소유권 분리는 대화 격리이며 사용량 분리를 뜻하지 않는다.

권장: 사용자별 질문 한도와 서버 전체 모델 호출·비용 한도를 별도로 둔다. 실제 사용자 한도 숫자는 예상 이용자 수와 사용 패턴을 보고 정해야 한다. 이번 리뷰에서는 임의로 설정하지 않았다.

### 2. 질문 1개가 모델 호출 1회를 뜻하지 않는다

현행 로컬 제품 대화는 답변 생성, 필요한 일반 숫자 문장 검증, 실패 답변 재작성, 재작성 결과의 숫자 검증까지 최대 4번의 모델 호출을 할 수 있다. 모두 같은 월 호출·비용 장부에 기록된다. 최종 답변이 검증 실패로 전달되지 않아도 이미 완료된 모델 호출은 사용량에 포함된다.

관리자 화면에는 현재 모델 호출 기록만 있고 사용자 질문 수·최종 성공 여부·호출 목적·부모 요청 ID는 없다. 내부 검증과 재작성을 별도로 구분하기 어렵다.

권장: 관리자에게 질문 수 / 모델 호출 수 / 성공·실패 / 생성·검증·재작성 비용을 구분해 표시한다. 사용자 개인 한도는 정상 처리한 질문을 기준으로 정하고, 내부 재작성 비용은 서버 비용 장부에서 관리하는 방향이 합리적이다.

### 3. ‘100% 중지’는 엄격한 예산 예약·차단이 아니다

호출 전에 완료된 장부만 확인하고, 호출이 끝난 뒤 비용을 기록한다. 검사와 기록 사이의 금액·횟수를 예약하지 않는다. 파일 기록에만 잠금이 있어 동시 요청은 같은 잔여량을 보고 모두 통과할 수 있다. workers=1이어도 동기 API 핸들러가 여러 스레드에서 실행될 수 있어 발생한다.

임시 장부로 실제 공급자 호출 없이 재현:

- 한도 1회에서 동시 요청 2개가 사전 검사를 통과했고 완료 장부가 2회가 됐다.
- 예산 1원, 기존 사용 0원에서 검사는 통과했다. 이후 테스트용 350원 비용 이벤트를 기록할 수 있었고 그 다음부터 중지 상태가 됐다. 실제 모델에 지출한 비용이 아니라 합성 토큰 사용량으로 검증한 것이다.

한 번의 응답 비용이 남은 예산을 넘는 경우도 같은 구조다. 현재 문구의 정확한 의미는 ‘기록된 누적 한도에 도달하면 다음 호출을 막음’이다.

권장: 사용자/요청별 실행 횟수 예약과 정산을 원자적으로 처리하고, 모델 입력·최대 출력 토큰을 제한한다. 예산도 예상 비용을 예약한 뒤 실제 사용량으로 정산해야 한다. 공급자 측 예산·알림 설정은 별도로 확인해야 하며 이번 리뷰에서 확인하지 않았다.

### 4. 80% 경고와 고정 안내가 실제 이용자 안내까지 이어지지 않는다

관리자 화면은 15초마다 집계해 경고를 표시한다. 하지만 현행 제품 대화의 정상 응답은 월 경고 스냅샷을 반환하지 않고, `quota`는 주로 한도 초과 예외에서만 채운다. 어시스턴트 안내에는 ‘월 200회·1만 원’이 문자열로 고정되어 있다. 서버 설정을 바꾸면 안내가 달라질 수 있다.

권장: 사용량 조회 API의 실제 값으로 안내하고, 경고와 중지를 구분한다. 사용자별 한도가 생기면 다른 사용자 사용량 대신 본인의 잔여량만 보여준다.

### 5. 원화 기록은 자체 추정치이며 청구 금액과 일치한다고 볼 수 없다

입력·출력 토큰에 코드의 고정 단가를 적용한다. `cached_tokens`는 기록하지만 현재 비용식에서 사용하지 않는다. 모르는 모델명은 `gpt-5-mini` 단가로 계산한다. 환율도 고정 가정이다. 이 리뷰에서는 현재 공급자의 공식 단가·청구서와 재정산하지 않았다.

또한 공급자 응답을 받기 전에 실패한 경우 비용을 확인하지 못할 수 있고, 장부 쓰기 실패는 경고 로그만 남긴 채 답변을 계속 반환한다. 그러면 제한에 쓰는 누적량이 실제보다 작을 수 있다. 질문 취소 버튼도 브라우저 요청을 중단하는 동작이며 이미 시작된 모델 호출의 취소·과금 중단을 보장하지 않는다.

권장: 모델·캐시·단가 버전·실제 토큰 사용량과 호출 상태를 기록하고 공급자 청구 내역과 정기 대조한다. 미확정·기록 실패 호출은 별도 상태로 남긴다. 예산 제한의 근거 장부는 기록 실패 때의 처리도 정해야 한다.

### 6. 기록 구조와 관리자 접근 경계를 정리해야 한다

현재 JSONL에는 사용자 ID, 요청 ID, 처리 단계, 성공·실패 정보가 없다. 여러 프로세스의 원자적 예약·정산도 지원하지 않는다. 손상된 JSON 줄은 집계에서 건너뛴다. 파일 백업·보존·이전 정책이 중요하다.

관리자 API는 QA 토큰이 비어 있으면 자체 검사 없이 통과한다. 운영과 로컬 모두 해당 토큰은 비어 있었다. 다만 저장소의 Nginx 템플릿은 `/api/admin/`에 별도 랩 인증을 적용하므로 ‘외부에 무인증 공개되어 있다’고 단정하지 않았다. 운영 외부 경계의 실제 인증 상태는 별도 검증이 필요하다. 관리자 프론트 클라이언트도 현재 QA 토큰 헤더를 따로 보내지 않는다.

권장: 운영 관리자 인증 경계를 명확히 하고, 계정의 관리자 역할로 장부 조회를 보호한다. 사용량·예약·정산은 영속 DB 또는 원자적 저장소에 두고 JSONL은 부가 감사 로그로 사용하는 방향이 적절하다.

## 권장 정책 구조

1. 사용자 이용량: 사용자별 질문 수와 동시 요청 제한. 실패·취소·내부 재작성 차감 기준을 명시한다.
2. 운영 안전장치: 서버 전체 월 비용·모델 호출 상한, 별도 관리자 시험 예산, 공급자 측 예산 알림.
3. 내부 원가: 답변 생성·출처 확인·재작성 등 실제 모델 호출을 모두 기록하되 한 질문에 연결한다.
4. 표시: 사용자에게는 본인의 이용량, 관리자에게는 전체 원가·실패율·사용자별 집계를 제공한다.
5. 정산: 호출 전 예약 → 호출 → 실제 토큰 비용 정산 → 예약 해제. 중간 실패·취소도 상태로 남긴다.

이용 제한은 질문 주제나 답변 형식 제한과 분리해야 한다. 비용을 아끼기 위해 허용 질문 목록이나 고정 답안으로 되돌릴 필요는 없다. 반복되는 제품 지식의 입력 최적화, 적절한 검증 호출, 요청당 자원 상한으로 관리할 수 있다.
