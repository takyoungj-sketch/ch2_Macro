### 7. 키 구성 기록 (`pipeline/collective/building_keys.py`)

- 이름 있는 키: `sha256(유형|addr1|addr2|addr3|name:건물명)`. **주소는 `addr3` 까지만** 쓴다.
- 이름 없는 키: `유형|addr1|addr2|addr3|addr4|지번|도로명`.
- `addr3` 는 구가 있는 시에서는 구(예: 안산시 → 상록구, addr4 = 동)이고, 그 밖에서는 읍면동(예: 평택시 → 평택동)이다.
- 그래서 구가 있는 시에서는 이름 키 하나가 구 전체의 같은 이름 건물을 묶는다. **C-01(동 분할)은 이 구조에서 생겼다.** 실측으로 C-01 대상 원장 51,450행·옛 키 1,531개는 모두 addr4(동)가 있는 행, 즉 구 있는 시였다.
- C-01 분할 키는 `원문 + "|emd:" + 동 단위 대표 법정동8` 로 동 단위가 된다(`split_key_from_raw`).
- **월간 integrity 검사 2(`pipeline/collective/integrity_p2.py`, `verify_monthly_integrity.py --collective`)** 가 이 구조를 잡는다.
  - 대상: 이름 키 중 동 이름(addr4, 없으면 addr3)이 2개 이상이면서 판정 목록(분할·유지) 밖인 키. → WARN(판정 대기열).
  - 그래서 새 동명 묶음이 생기면 월간에 드러난다.

## 느린 쿼리 원인 (EXPLAIN)

- `rep_address_query` 마지막 조인 `b.x IS NOT DISTINCT FROM r.x` 는 해시·머지 조인이 안 된다.
  - 그래서 **Nested Loop + Join Filter**(base 행 × 그룹 행)가 된다.
  - 경기 연도별: base 1,546,646행 × 그룹 230,701 = 3.57×10¹¹ 비교.
- 계획 비용(경기 연도별):
  - 옛 조인 3.4×10⁹
  - `=` 조인 3.2×10⁶ (Hash Join)
  - 원래 MAX 주소 SQL 0.79×10⁶
- 세종 연도별 EXPLAIN ANALYZE:

  | SQL | 시간 | 비고 |
  |---|---|---|
  | 옛 조인 | 8,185ms | Join Filter 제거 88,935,750행 |
  | `=` 조인 | 268ms | NULL 검사 넣은 뒤 520ms |
  | MAX 주소 SQL | 667ms | |

  결과 행은 42,050으로 모두 같다.
- 그룹 열 NULL:
  - `collective_transactions` building_key·asset_type 0.
  - 임대는 base 가 계산 키라 NULL 없음.
