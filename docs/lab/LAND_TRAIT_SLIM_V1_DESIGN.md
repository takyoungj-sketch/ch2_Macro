읽는 법:

- **전국 충돌 4,365만 키가 전부 표기 충돌이다.** 지목·면적·용도지역·이용상황·높이·형상·도로 코드와 공시지가가 모두 같고 명칭만 다르다. 의미가 다른 충돌은 0건이다. slim에서는 이 키를 모두 정상 관측으로 접을 수 있다. 원장 관측 970,577,839에 이 키만큼 관측이 더해지는 효과다.
- **코드 구간은 원장 행의 22~24%다.** 같은 코드가 여러 기준일·기준연도에 반복된 행을 접으면 전국 약 2.2억~2.4억 행으로 추정된다.
- **공시지가가 가장 크다.** 필지 × 기준연도 가격이 원장 행의 55~72%다. 원천 파일이 과거 연도 가격을 함께 싣기 때문이다. 구축 때 연도 분포를 재고, 거래 연결에 쓰지 않는 오래된 연도를 뺄지 정한다.
- **코드사전:** 지목·용도지역·높이는 코드당 명칭이 하나다. 이용상황 10~11개, 형상 5개, 도로 5개 코드는 명칭 변형이 둘 이상이다(띄어쓰기·표기 변경). 빈 명칭 행이 청주 28%, 표본3 11%로, 2022년 이후 판의 명칭 누락이다.

## 표

별도 파일 `C:\CH2\parcel_master\land_trait_slim_v1.sqlite`. 원장 파일과 섞지 않는다.

| 표 | 내용 |
|---|---|
| `asof_calendar` | 기준일 31개와 비트 번호 |
| `code_dictionary` | 항목·코드·명칭·행수·표준 여부. 표준 명칭은 빈 값이 아닌 것 중 가장 많은 명칭 |
| `trait_interval` | 필지, 처음·마지막 기준일, 관측 기준일 비트마스크, 지목·면적·용도지역1·2·이용상황·높이·형상·도로 코드. 연속된 관측에서 코드 묶음이 바뀔 때만 새 행 |
| `price` | 필지, 기준연도, 공시지가, 같은 연도에 가격이 둘 이상이면 충돌 표시 |
| `build_info` | 원장 해시, 원장·충돌 행수, 생성 시각, 스크립트 버전 |

비트마스크로 구간 안에서 실제로 관측된 기준일을 모두 남긴다. 그래서 "계약일 직전 판"이 원장과 같은 날짜로 나온다. 한 기준일 안에서 기준연도 행끼리 코드 묶음이 다르면 그 구간에 표시를 남기고 건수를 보고한다.

## 검증 기준 — 계획 문서의 완료 조건을 바꾼다

계획 문서는 "slim으로 V1을 다시 돌려 결과표 건수가 같아야 한다"였다. 이 조건은 맞출 수 없다. V1은 원문 명칭으로 비교하고, 빈 명칭 때문에 생긴 충돌을 "표기 정규화"로 따로 다룬다. slim은 그 명칭 문제를 코드사전으로 없애는 것이 목적이라서, slim 위에서 V1을 돌리면 일부 연결 결과가 달라지는 것이 정상이다. 원문 명칭까지 slim에 넣으면 원장을 한 벌 더 만드는 것과 같다.

대신 다음 세 가지로 검증한다.

1. **무손실:** 청주 4구와 강남·처인·경주에서 원장의 모든 관측(정상 + 충돌)을 slim에서 되살렸을 때 코드·면적·공시지가가 같다. 차이 0건.
2. **전국 합계:** slim의 필지·기준일 관측 수가 원장 정상과 충돌 키의 합집합과 같다. 공시지가 행과 충돌 표시 건수가 원장에서 직접 센 값과 같다.
3. **V1 결과는 그대로 둔다:** 지금 결과표는 V1로 고정한다. slim 위의 연결은 V1.1(계획 7단계)에서 돌리고, 그때 V1과의 차이를 상태별로 보고한다.

## 비용

가늠 속도(청주 1,787만 행에 138초)로 보면 전국 약 10.6억 행을 한 번 읽는 데 2~3시간이다. 결과 파일은 구간 약 2.3억 행과 공시지가 행을 합쳐 수십 GB로 예상한다. 정확한 크기는 구축 후 적는다.

## PostgreSQL

전 필지 slim은 로컬 파일로만 둔다. PostgreSQL에는 쓰는 곳이 정해질 때(복합 4단계, 집합 5단계) 그 소비자가 가리키는 필지만 올린다.
