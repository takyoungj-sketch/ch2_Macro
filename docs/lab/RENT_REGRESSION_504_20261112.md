## 5. 고치는 방향 (원래부터이므로 안만, 승인 전 미적용)

- A. 조회 조건을 `t.building_key IN :keys` 로 바꾼다(인덱스 사용). 빈 키 행은 계산 키로 따로 찾는다.
  빈 키 행이 운영에 367만 행 있어, 빈 키 단지까지 맞추려면 그 부분만 계산식 조건을 쓰되 시군구 등으로 범위를 좁혀야 한다.
- B. 계산식 그대로 식 인덱스 생성 (`CREATE INDEX CONCURRENTLY ... ((COALESCE(...)))`) — 코드 변경 없음, 운영 DB 변경이라 별도 승인.
- C. 회귀 경로에 `statement_timeout`(예: 100초)을 걸어 nginx가 끊은 뒤 DB가 계속 도는 것을 막는다.

T 결정(2026-11-12): **C + 화면 수정만** 진행. A는 D-085 임대 회귀 공개 조건으로 넘기고, B는 하지 않는다.

## 6. 적용 (브랜치 `fix/rent-regression-timeout`)

### 서버
- `backend/app/rent/query_guard.py` `heavy_query()` — 트랜잭션 범위 `statement_timeout`
  (기본 90초, `RENT_HEAVY_STATEMENT_TIMEOUT_MS`로 조정). 초과(PostgreSQL 57014)면 롤백 후 **503 + 안내 문구**.
  정상 종료면 원래 값으로 되돌린다. 다른 DB 오류는 그대로 올린다.
- 적용 위치(`backend/app/rent/tx_query.py`):
  - `fetch_regression_rows` — 단지 회귀·통합 회귀 둘 다. 503 문구 "이 단지는 거래가 많아 지금은 분석할 수 없습니다. 잠시 뒤 다시 시도해 주세요."
  - `list_building_transactions`의 마지막 계산 키 대체 조회 — 503 문구 "거래 목록을 찾는 데 시간이 너무 오래 걸려 중단했습니다. …"
- 임대에는 별도 "예측" API가 없다. 예측값은 같은 회귀 실행 응답 안에서 계산되므로 회귀 경로 제한으로 함께 막힌다.

### 화면 (`frontend-rent`)
- 회귀 요청 상한 110초(`RENT_REGRESSION_TIMEOUT_MS`): 서버 DB 제한 90초보다 길고 nginx 120초보다 짧다.
- `rentRegressionErrorMessage()` — 시간 초과·504/502·503·입력 오류(400 detail)·연결 실패를 각각 다른 문구로.
  실패 뒤 버튼은 다시 "회귀 실행"으로 돌아와 다시 누를 수 있다.

### 화면 재현 (로컬 하네스, 2026-11-12)

nginx처럼 120초 뒤 HTML 504를 주는 모의 서버에 수정 전(origin/main)·수정 후 회귀 패널을 동시에 붙여 실행.

| 경과 | 수정 전 | 수정 후 |
|---|---|---|
| 0~110초 | "실행 중…" | "실행 중…" |
| 111초 | "실행 중…" | "응답이 110초 안에 오지 않아 중단했습니다. 거래가 많은 단지는 지금 분석할 수 없을 수 있습니다. 잠시 뒤 다시 시도해 주세요." · 버튼 복귀 |
| 121초 | 일반 문구 "회귀를 실행하지 못했습니다." · 버튼 복귀 | (같음) |

- 수정 전에도 120초 뒤 일반 문구는 실제로 뜬다. 다만 2분 동안 진행 표시만 있어 멈춘 것으로 보였다.
- 503(서버 시간 제한) 응답은 수정 전·후 모두 서버 문구를 그대로 보여 주고 버튼을 다시 누를 수 있다.
- 운영에서는 서버 제한 90초가 먼저 걸리므로 화면은 보통 90초 안팎에 503 문구를 받는다. 110초 상한은 그보다 늦을 때의 안전장치다.

## 7. `building_key_sql`(계산 키) 사용 임대 API 전수

| API | 계산 키 위치 | 예상 스캔 범위 | 운영 관측(PG 느린 쿼리 로그, 11-01~11-12, 5초 이상) | 위험 | 조치 |
|---|---|---|---|---|---|
| `POST /api/rent/buildings/{key}/regression/run` | WHERE `IN :keys` | 자산 유형 전체(아파트 약 762만 행) | 167~388초 4회 → 모두 504 | **높음** | 시간 제한 + 503 |
| `POST /api/rent/regression/run` (통합) | 같은 함수 | 같음 | 기록 없음(같은 쿼리) | **높음** | 시간 제한 + 503 |
| `GET /api/rent/buildings/{key}/transactions` | 3단계 중 마지막 대체 조회 WHERE `= :bk` | 원장 키·마트 주소로 0건일 때만 실행. 이때 유효 원장 전체(약 1,489만 행) | 기록 없음 | 중간(없는 키·옛 키로 호출하면 전체 스캔) | 시간 제한 + 503 |

- 낮음 두 경로는 지역 범위가 먼저 걸려 원장 전체를 보지 않는다. 시간 제한을 걸면 기존에 120초 안에 끝나던 목록 화면을 503으로 바꿀 위험만 생겨 그대로 둔다.
- 5초 이상만 기록되므로(`log_min_duration_statement=5s`) 기록 없음 = 5초 미만.
- 참고: 원인 확인 때 운영 DB에서 빈 키 행 수 집계(읽기 전용 `count(*)`) 1회를 실행했고 46초 걸렸다.


## 8. T 조건부 승인 보완 (2026-11-14)

- 단지·통합 회귀와 거래목록 요청은 동기 DB 작업 전 하나의 monotonic 마감을 만든다(기본 90초).
- 거래목록의 저장 키·주소·계산 키 경로와 COUNT/목록 SQL 전부 같은 예산을 공유한다.
- SQL마다 남은 시간으로 트랜잭션 로컬 statement_timeout을 갱신하며, 예산 소진 시 SQL 없이 503.
- 환경변수는 100초가 상한이며 초과 입력은 값 노출 없이 경고한다.
- 정상 종료는 기존 설정 복원, 예외는 rollback(실패 시 연결 invalidate)한다.
- 거래목록 503은 자동 재시도하지 않고 안내를 표시한다. 회귀 오류는 AI facts나 분석 캐시에 전달하지 않는다.
- 정상 HTTP 200, 합산 마감 503, 만료 후 SQL 미실행, PostgreSQL 취소 및 동일 물리 연결 풀 재사용 테스트 추가.
- PostgreSQL 접속 불가 환경은 skip. 접속 이후 검증 오류는 실패로 유지한다.
- 새 테스트 13건은 운영 DB SSH 터널에서 통과(원장 없이 짧은 pg_sleep/SELECT만 실행).
- 배포는 기존 13개 실패·수집 오류 1개 외 새 실패 0, 운영 파일 차이 제한, 배포 단독 진행을 모두 확인한 뒤 수행한다.
