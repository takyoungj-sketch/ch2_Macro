## 1. 결론 먼저

**이것은 PNU 키의 부동산 속성 DB이지, 「건축물이 있는 토지 DB」가 아니다.** 필지를 바탕에 두고 그 위에 건물을 얹는 구조가 맞다. 추측이 아니라 원본이 그렇게 생겼다 — 표제부·총괄·토지대장·AL_D155·AL_D151·K-apt가 **전부** 법정동코드 + 본번 + 부번을 갖고, K-apt는 필지고유번호를 직접 준다(§2). 적재는 수요 필지다(§9). 지역지구구역은 폐기(§6.3). AL_D151은 2026-08-25에 집합 마트로 먼저 붙었고, 축약 DB 그레인은 `(pnu, price_year)`다(§5.5).

그런데 제안의 핵심은 스키마가 아니라 **이 DB를 어디에 두느냐**다. 결론은 **운영 서버에 올리지 않는다.** 축약대장은 제품이 조회하는 DB가 아니라 **값을 만들어내는 재료**다. 로컬에서 만들고, 결과 컬럼만 도메인 DB에 실어 보낸다(§4). 이건 VPS가 4GB RAM / 80GB SSD라는 제약에서 나온 타협이 아니라, 이미 `region_codes` 를 그렇게 쓰고 있는 기존 패턴과 같은 철학이다.

그리고 측정 과정에서 **복합과 집합의 난이도가 전혀 다르다**는 걸 확인했다. 복합은 지번이 마스킹돼 있어 확률적 매칭이고 정확도 인증이 필요하다. 집합은 **지번이 100% 온전해서 결정론적 조인**이다(§3). 그래서 집합부터 착수하는 것이 위험이 낮다.

## 2. 왜 필지가 자연 키인가

여섯 개 원본의 지역·지번 표현을 실제로 확인했다.

| 원본 | 필지 식별 방식 | 실측 |
|---|---|---|
| 건축물대장 표제부 `mart_djy_03.txt` | `[8]`시군구 + `[9]`법정동 + `[11]`본번 + `[12]`부번 | 806만 행 / **595만 필지** |
| 총괄표제부 `mart_djy_02.txt` | `[10]`+`[11]`+`[13]`+`[14]` | 62.1만 행 / 61.7만 필지 |
| 토지대장 `AL_D003` | `법정동코드` + `지번` | **16시도** (`20260807`) |
| 토지이용계획 `AL_D155` | `법정동코드` + `지번` | **16시도** (`20260809`) |
| 개별공시지가 `AL_D151` | `법정동코드` + `지번` (PNU) | **16시도** · 광주 `29`·전남 `46` 구코드 → 통합 `12` |
| ~~지역지구구역 `mart_shtreg_10.txt`~~ | — | **폐기**(§6.3) |
| K-apt 단지 | **PNU 19자리 직접 제공** | 21,687단지 |
| 복합 실거래 | 마스킹 지번 → 복원 | 충북 81.5% · 서울 68.1% |
| 집합 실거래 | 지번 **마스킹 없음** | 아파트 99.7% 변환 가능 |

**K-apt가 결정적이다.** `20260814_단지_필지고유번호.xlsx` 는 「고유번호(19자리) ↔ 단지코드」 두 컬럼짜리 파일이고, 21,687단지 **전부**에 대해 PNU를 준다. 주 1회 갱신된다.

```
1111011800100720000  ←→  A11007001   (서울 종로구 내수동 72, 경희궁의아침3단지)
   └법정동10┘│└본번┘└부번┘
             └ 필지구분(1=토지, 2=산)
```

지금 우리는 K-apt를 **주소 문자열로** 매칭한다(`beopjungri_code` + 지번 파싱, 또는 단지명). 그런데 K-apt 법정동주소는 깨져 있는 경우가 있다 — A10021295는 주소가 「서울특별시 종로구 내수동 73-」로 부번이 잘려 있는데 **PNU는 `...100730000` 으로 온전하다.** 문자열 파싱을 PNU 조회로 바꾸면 이 부류의 실패가 사라진다.

집합 쪽에는 PNU가 있다. `parcel_master.parcel.pnu`와 `collective_stats.builder_master.pnu`다. 복합 매칭(`recover_address.py`)은 여전히 `(법정동코드, 본번, 부번)` 튜플과 `_cache/*.json`으로 원본을 다시 훑는다. 축약 DB를 승격하는 이유는 이 경로를 SQL 조인으로 바꾸는 것이다.

## 3. 결정적 차이 — 집합은 매칭이 필요 없다

복합 데이터 보강이 어려웠던 이유는 전부 마스킹 때문이었다. 집합은 그 문제가 없다. 실측했다.

| 집합 유형 | 거래 | 지번 마스킹 | PNU 변환 가능 | 필지 | `building_key` |
|---|---|---|---|---|---|
| 아파트 | 4,495,834 | **0.0%** | **99.7%** | 43,354 | 45,743 |
| 연립·다세대 | 1,102,907 | **0.0%** | **99.9%** | 206,023 | 200,923 |
| 오피스텔 | 348,312 | **0.0%** | **100.0%** | 13,776 | 13,522 |
| 분양권 | 537,143 | 0.0% | 80.5% | 5,156 | 5,785 |

두 가지를 읽어야 한다.

**첫째, 집합 보강에는 「매칭 정확도」라는 개념이 없다.** 지번이 그대로 있으니 PNU를 만들어 조회하면 끝이다. 복합에서 우리를 괴롭힌 판별력·혼입·스냅샷 충돌이 전부 해당 없다. 인증 문턱을 세울 필요도 없다. 남는 건 **커버리지**뿐이고, 그건 대장에 그 필지가 있느냐의 문제다.

**둘째, `building_key` 와 필지가 거의 1:1이다.** 아파트 45,743개 키에 필지 43,354개다. 즉 PNU를 `building_key` 에 붙이는 것이 자연스럽고, 기존 키 체계를 갈아엎을 필요가 없다.

분양권 80.5%는 예외다. 나머지는 `BL-1`·`BL-A2` 같은 **블록-로트 표기**로, 지번이 아직 확정되지 않은 신규 택지다. 이건 매칭 실패가 아니라 **원천에 지번이 없는 것**이므로 보강 대상에서 제외한다.

## 4. 이 DB는 운영 서버에 올리지 않는다

가장 중요한 설계 결정이다.

### 지금의 구조

배치는 **로컬 PC에서** 돌리고, 검증 후 `pg_dump` 로 VPS에 promote한다. VPS는 Lightsail 4GB RAM / 80GB SSD이고 `land_stats` 하나가 이미 약 7GB다. 도메인 DB는 물리적으로 분리돼 있어(`land_stats` / `built_stats` / `collective_stats` / `rent_stats`) DB를 넘는 조인이 애초에 안 된다. 그래서 `region_codes` 는 **네 DB에 각각 복사본**으로 들어가 있다.

### 그래서 축약대장의 위치

축약대장은 **로컬 전용 다섯 번째 DB**(`parcel_master`)로 둔다. VPS에 올리지 않는다.

```
로컬 (배치 전용)                         VPS (운영)
┌────────────────────────┐
│ parcel_master          │
│  parcel · parcel_zone  │   매칭·조인
│  building · danji      │   ────────┐
└────────────────────────┘           │
                                     ▼
                        ┌────────────────────────────┐
   promote (pg_dump)    │ built_stats                │
   ◄────────────────────│  built_transaction_        │
                        │    enrichment              │
                        ├────────────────────────────┤
                        │ collective_stats           │
                        │  collective_building_      │
                        │    attributes (+pnu)       │
                        └────────────────────────────┘
```

저장소는 세 층이다. **(A)** MOLIT 원장(도메인 DB, 덮지 않음) · **(B)** 로컬 `parcel_master` 속성 · **(C)** 매칭 결과(`built_transaction_enrichment` 등, promote 대상). 분석은 opt-in LEFT JOIN이다. 기본통계 마트는 (A)만 쓴다.

이유가 세 개다.

**사용자가 조회하는 것은 필지가 아니라 거래다.** 거래목록에서 구조·용도지역을 보여주려면 「이 거래의 구조는 철근콘크리트」라는 **결과**만 있으면 된다. 그 결과를 만들기 위해 595만 필지를 훑는 일은 빌드 타임에 끝난다. 운영 서버가 필지 테이블을 가질 이유가 없다.

**용량이 맞지 않는다.** `parcel` 595만 행 + `building` 806만 행 × 3스냅샷 + `parcel_zone` 을 인덱스까지 얹으면 수 GB다. VPS 여유가 25GB 남짓인데 여기에 쓸 값이 없다.

**동결 정책과 맞물린다.** D-047이 정한 대로 확정된 보강 행은 **동결**한다. 그러면 운영 DB의 보강 값은 한 번 정해지고 안 바뀐다. 재계산 재료를 운영 서버에 둘 필요가 없다는 뜻이다.

## 5. 스키마 — 실제 테이블과 추가 설계

파일럿에서 `danji` 테이블은 만들지 않았다. 시공사는 기존 `collective_stats.builder_master`에 `pnu`를 붙였다(§5.4). 로컬 실체 테이블은 `parcel` · `parcel_zone` · `building` · `parcel_land_price` · `ledger_snapshot` · `match_revision`(빈 자리)이다.

### 5.1 `parcel` — 필지

수요 필지만(거래·단지·표제부가 가리키는 PNU). 전국 3,900만 빈 필지·「건물 있는 595만」 전량 선적재는 하지 않는다(§9).

| 컬럼 | 비고 |
|---|---|
| `pnu` CHAR(19) **PK** | 법정동10 + 필지구분1 + 본번4 + 부번4 |
| `beopjungri_code` CHAR(10) · `bun` CHAR(4) · `ji` CHAR(4) | 조인·조회용 분해 컬럼 |
| `sido_code` CHAR(2) · `sigungu_code` CHAR(5) | 지역 필터 |
| `jimok_code` CHAR(2) | 토지대장. 미확보 시도는 NULL |
| `land_area` NUMERIC | 토지대장 우선, 없으면 대장 대지면적 |
| `land_area_source` VARCHAR | `land_ledger` / `title` / `summary` |
| `first_seen` · `last_seen` | 스냅샷 범위 |

### 5.2 `parcel_zone` — 용도지역 (복수 라벨)

D-047이 정한 대로 단일 컬럼이 아니라 **행 단위 복수 라벨**이다. 필지가 두 용도지역에 걸치는 경우가 충북 8.7%·서울 9.4%다.

| 컬럼 | 비고 |
|---|---|
| `pnu` CHAR(19) · `zone_label` VARCHAR **PK(둘)** | |
| `zone_family` VARCHAR | 주거 / 상업 / 공업 / 녹지 / 관리 / 농림 / 자연환경 |
| **`is_coarse` BOOLEAN** | 「도시지역」·「관리지역」 등 상위 분류 여부 |
| `source` VARCHAR | `al_d155` / `shtreg` |
| `snapshot` VARCHAR | |

**`is_coarse` 는 어제 잡은 버그의 직접적 산물이다.** AL_D155의 대분류 라벨(「도시지역」)을 코드로 걸러내려 했는데 코드 체계가 시군구 단위로 달라 서울 34.2%·충북 0.4%가 샜다([`BUILT_DATA_ENRICHMENT.md`](BUILT_DATA_ENRICHMENT.md) §6 말미). 대분류를 **버리지 않고 플래그로 표시**하면 조회 쪽이 `WHERE NOT is_coarse` 한 줄로 안전해지고, 검증로봇의 「채운 값이 상위 분류면 실패」 규칙이 SQL 한 줄이 된다. 판정 로직이 파이프라인 안쪽에 숨지 않는다.

### 5.3 `building` — 건물 (동 단위)

세 스냅샷을 모두 보관하는 이유는 D-047 §7이다. **최신 대장이 최선이 아니다** — 과거 거래는 과거 대장과 더 잘 맞는다(증축·용도변경 때문). 합집합 전략이 충북 78.8% → 81.5%를 만든 근거이므로 스냅샷을 접으면 안 된다.

### 5.4 `danji` — 만들지 않음

**시공사의 유일한 출처는 K-apt다.** 건축물대장 표제부에는 시공사가 없다(77개 컬럼 전수 확인). 초안은 `danji` 테이블을 제안했으나 **새 테이블을 만들지 않고 `builder_master`에 `pnu` 컬럼을 추가**했다. 이 절의 채움률 표는 그 근거로만 남긴다.

| K-apt 컬럼 | 채움률 (21,687단지) |
|---|---|
| 시공사 | **100.0%** |
| 세대수 | **100.0%** |
| 최고층수 | 100.0% |
| 사용승인일 | 100.0% |
| 단지분류 | 99.5% |
| 건물구조 | 97.5% |

### 5.5 `parcel_land_price` — 개별공시지가 (추가)

그레인 `(pnu, price_year)`. AL_D151을 필지·기준연도 단위로 보관해 복합·집합이 공용한다. 연도 이력은 재료 보존이다. **제품은 최신 대표 필지 1개의 원값만 쓴다.** 거래연도별 공시지가 정합은 하지 않는다(집합 지역회귀 결정, 2026-08-25).

현재 `collective_stats.collective_building_assessed_land_price`는 그레인이 `(building_key, asset_type)`인 **파생 마트**다. 축약 DB 적재 뒤에는 이 마트가 `parcel_land_price`에서 최신 연도를 골라 채운다. 광주·전남 구코드 `29`/`46` → 통합 `12` 매핑은 [`pipeline/collective/import_assessed_land_price.py`](../pipeline/collective/import_assessed_land_price.py)와 같다.

| 컬럼 | 비고 |
|---|---|
| `pnu` CHAR(19) · `price_year` SMALLINT **PK** | |
| `price_per_m2` NUMERIC | ㎡당 원 |
| `base_date` DATE | 공시일 (있으면) |
| `source_sido` CHAR(2) | 원본 폴더 코드. 구코드 보존 |

### 5.6 `ledger_snapshot` — 판본 레지스트리 (추가)

## 6. 무엇이 채워지는가

### 6.1 복합 — 이미 인증된 경로

충북 81.5% · 서울 68.1%의 거래에서 지번이 확정되고 구조·용도지역이 동시에 채워진다. 축약대장이 바꾸는 것은 **정확도가 아니라 실행 방식**이다. 지금은 매칭 한 번에 3.5GB를 훑고 서울 3스냅샷이 14분 걸린다. `parcel` + `building` 이 DB에 있으면 SQL 조인이 된다. **원본 삭제는 2019+ 동등 재현 게이트 통과 후**다. 지금 지우면 `recover_address.py`가 멈춘다. 보강 범위는 계약 2019년 이후만(D-050).

### 6.2 집합 — K-apt와 표제부가 상보적이다

집합 지역회귀([`D-045`](lab/decisions/D-045.json))가 필요한 변수는 세대수·층수·연식·구조·용도지역·시공사다. 두 원본의 역할이 다르다.

| 변수 | K-apt (21,687단지) | 표제부 `집합` (65.9만 동) |
|---|---|---|
| 시공사 | **유일 출처** 100% | 없음 |
| 세대수 | 100% | 72.3% |
| 최고층수 | 100% | 있음 |
| 구조 | 97.5% | 있음 |
| 사용승인일 | 100% | 있음 |
| 주차 대수 | 있음 | 옥내외 기계식·자주식 `[50][52][54][56]` 합 (면적 열 제외) |
| 난방·복도유형 | 있음 | 없음 |
| **연립·다세대·오피스텔** | **거의 없음** | **있음** |

K-apt는 **의무관리대상 공동주택**만이다. 아파트 `building_key` 45,743개에 K-apt 단지는 21,687개 — 절반이 비어 있고, 연립·다세대 200,923개와 오피스텔 13,522개는 사실상 전부 비어 있다. 현재 속성 커버리지가 단지 기준 58%에 머무는 이유다.

**표제부 `집합` 65.9만 동이 그 빈칸을 메운다.** 시공사는 못 채우지만 세대수·층수·구조·승인일·주차대수는 채운다. 목록 채움은 `apply_title_fill`(tier T). **아파트**는 K-apt 없는 Z만, **연립·오피스텔**은 유형별 동만 합쳐 INSERT. 같은 필지의 아파트 동을 연립 행에 넣지 않는다. 오피스텔 `[40]` 세대수가 비면 `[66]` 호수를 제품 세대수로 쓴다(2026-07 집합 오피스텔 동 45.6%). 아파트·연립에는 호수 대체를 쓰지 않는다. 지역회귀 hard 표본은 계속 A·B·C.

주용도 분포(표제부 `집합`)를 보면 아파트 계열 약 23.9만 동, 다세대 11.4만 동, 연립 2.0만 동이다. 연립·다세대 보강 폭이 가장 크다.

### 6.3 용도지역 — 지역지구구역 대장은 AL_D155를 대체하지 못한다 (측정 완료)

지금 용도지역은 AL_D155를 시도별로 받아야 하고 파일이 시도당 2.5GB다. 17개 시도면 40GB를 훑어야 한다. 이것을 한 파일로 대체할 후보로 건축HUB 「지역지구구역」 대장을 지목했었다. **2026-08-22 현행판을 확보해 실측한 결과 대체 불가로 판정한다.**

측정 대상은 `raw addition/지역지구구역(건축허브)/국토교통부_건축물대장_지역지구구역+(2026년+07월)/mart_djy_10.txt` (1,745MB · 8,127,476행)이다. 어제 본 폐쇄말소 이력본(411MB)이 아니라 별도 계열의 현행 배포본이다.

**형식은 기대대로 좋았다.** 구분 컬럼이 명시적이고(`용도지역코드` 5,644,493 · `용도구역코드` 1,351,917 · `용도지구코드` 1,131,066), 코드·표준명·지자체 원문명이 따로 있다. 커버리지도 전국 18시도 4,102,342필지(라벨이 있는 것 3,803,700)이고 **행정코드가 전부 통합 신코드**다(`12` 전남광주 631,942 · `51` 강원특별 319,883 · `52` 전북특별 354,814, 구코드 `29`·`42`·`45`·`46` 0건). 복수 용도지역 필지는 12.0%로 AL_D155의 9%대와 비슷하다.

**그런데 내용이 현행 용도지역이 아니다.** 서울·충북에서 AL_D155와 같은 필지끼리 대조했다.

| | 서울 | 충북 |
|---|---|---|
| AL_D155 필지 | 44,190 | 28,378 |
| 이 대장이 용도지역을 주는 것 | 24,704 (55.9%) | 18,439 (65.0%) |
| 그중 일치 | 15,709 (63.6%) | 13,771 (74.7%) |
| 그중 불일치 | 8,995 (**36.4%**) | 4,668 (**25.3%**) |
| 구법 라벨 포함 | 28.5% | 12.1% |
| **결국 옳은 값을 얻는 필지** | **35.5%** | **48.5%** |

마지막 줄이 핵심이다. 이 대장만으로 용도지역을 채우면 **서울 필지의 35.5%, 충북의 48.5%만 옳은 값을 얻는다.** AL_D155는 같은 필지에서 각각 100%를 준다.

불일치의 정체는 세분화 이전 제도다. 「일반주거지역」(633,308행)·「준농림지역」(203,608행)·「전용주거지역」은 2003년 국토계획법 시행 전 표기이고, AL_D155는 같은 필지를 제1·2·3종일반주거지역으로 준다. 「계획관리지역」이 「관리지역」으로 강등된 사례도 있다. 지자체 원문명 컬럼은 구제가 되지 않는다 — 오히려 「일반주거」·「주거」처럼 더 거칠고 949,239행이 빈값이다.

**결정적 증거는 생성일이다.** 용도지역 행의 **89.4%(5,046,929건)가 2022년에 만들어진 뒤 갱신되지 않았다**(2023 182,079 · 2024 135,476 · 2025 121,892 · 2026 158,116). 즉 이 대장은 2022년 이관 시점의 **건축 인허가 당시 용도지역**을 담고, 이후 신규 허가분만 추가된다. 도시계획 변경을 따라가지 않는다.

가장 위험한 부류는 구법 문제조차 아니다. AL_D155가 제2종일반주거지역인 필지를 이 대장은 **제1종일반주거지역**으로 준다. 종이 다르면 용적률이 달라 가격에 직결되는데 라벨만 보면 정상이라 걸러지지 않는다. 「사용자는 오류 하나로 신뢰를 잃는다」는 전제에서 23~32% 불일치는 자격 미달이다.

**따라서 AL_D155 시도별 수집을 계속한다.** §6.3이 약속했던 40GB → 411MB 절약은 없다. 이 대장은 용도지역 원천으로도, 매칭 검증축으로도 쓰지 않는다(용도지역은 교란 86.7%로 이미 검증축에서 배제됐다).

재현: `python pipeline/built/_tmp_shtreg_probe.py` (전량 스캔 45초, 이후 `_cache/shtreg_zone.json` 재사용).

### 6.4 전국 확장 걸림돌 하나 해소

미해결로 남겨뒀던 시군구코드 문제를 확인했다. 표제부 2026-07의 시도코드 분포는 통합 신코드를 쓴다 — `12`(전남광주통합특별시) **928,704행**, `51`(강원특별) 477,226, `52`(전북특별) 513,966이고 구코드 `29`·`42`·`45`는 0건, `46`은 13건만 남아 있다. `built_transactions` 의 sido `12` 와 정합한다. **코드 불일치로 23%를 잃는 시나리오는 발생하지 않는다.**

### 월간 배치에 추가되는 것

현행 순서는 `run_land_cycle_csv` → `run_built_cycle_csv` → `run_collective_cycle_csv` 이고, 각 도메인이 최근 12개 계약월을 purge하고 재적재한다. 보강이 붙으면 **마트 뒤에** enrich를 둔다. 기본통계 마트는 국토부 원장만 쓴다.

```
1. 실거래 UPSERT + CSV에 없는 해시만 DELETE  (P3.1)
2. 마트 빌드                        (현행. 보강 컬럼 없음)
3. enrich  ← 미구현
     복합: 보강표에 없는 hash만, contract_year >= 2019.
     집합: 신규 building_key만 PNU 조인. 기존 A·B·C는 덮지 않음.
4. 스냅샷 · 검증                    확정 행 값 변경 = 0, 고아 보강 행 수
```

**복합의 「확정 행 동결」은 타협이 아니라 요구사항이다.** 스냅샷마다 매칭 결과가 다르다는 것이 D-047 §7의 실측이다. 매월 재매칭하면 지난달 벽돌구조가 이번달 철골구조로 바뀔 수 있고, 그건 오류율보다 심각한 신뢰 파괴다. 대신 **미상 행은 새 대장이 올 때마다 재시도해도 안전하다** — 빈칸이 채워지는 방향은 개선으로만 보인다.

**집합은 동결이 필요 없다.** 결정론적 조인이라 같은 지번이면 항상 같은 PNU이고 값이 흔들리지 않는다. 오히려 지금의 `building_key`(주소+단지명 해시)보다 PNU가 안정적이다 — 원장 표기가 바뀌면 해시는 바뀌지만 PNU는 안 바뀐다.

### 원본 파일을 지울 수 있게 된다

지금은 매칭을 위해 `raw addition`을 들고 있어야 한다. SQL 조인 이관이 **2019+ 498,568행 · 75.0% · A1/A2 구성비**를 재현한 뒤에만 원본을 다음 분기까지 지울 수 있다. 게이트 전 삭제는 금지.

| **5** | `parcel_zone` 전국화 | AL_D155 전국 적재. 지역지구구역 대체안은 §6.3에서 폐기 | **원본 16시도 확보. Track B 대조·복합 감사 후. 48GB라 지금은 안 넣음** |

**2단계가 검증 관문이다.** PNU 조인 결과를 기존 주소 매칭 결과와 대조해서, 늘어난 매칭이 실제로 옳은지 확인한 뒤에만 3단계로 간다. 여기서 「PNU가 가리키는 단지와 주소 매칭이 가리키는 단지가 다른」 건이 나오면 그게 신호다.

2026-08-25: 단계 1~3은 집합 범위로 완료. 단계 5 `parcel_zone`은 집합 필지 기준 적재. 단계 4 복합 enrichment는 원본 재스캔으로 로컬 적재됐고, 축약 SQL 이관은 Track C(구현 계획 P2).

### 8.2 승인된 작업 순서 (2026-08-22) — 화면과 적재를 나눈다

전국 축약 DB와 지역회귀 UI를 한 줄로 묶지 않는다. 지역회귀가 쓰는 단지 속성(`collective_building_attributes`)은 **이미 전국 아파트**에 있다.

| 트랙 | 범위 | 하는 일 | 안 하는 일 |
|---|---|---|---|
| **A 지역회귀 UI (우선)** | 유형=아파트. 화면은 지역 잠금 없음. 검토는 대전·충북 | 통계분석 아래 「지역회귀」모달. 한 행=단지. `building_stats`⋈`attributes` 실시간 조인 | 새 마트 · 연립·비주거 · 헤도닉 P3 |
| **B 축약대장 파일럿** | 표제부 **「집합」** + 시도 **`30`·`43`** 3스냅샷 | `parcel`/`building`에 행만 제한해 적재. `builder_master.pnu` 대조 | 시도별 테이블 분리 · 전국 11 GB 선적재 · AL_D155 48 GB |
| **C 복합 이관** | 「일반」 표제부 + SQL 조인 | 3단계: 일반 적재 → `time_fallback`·A2·대표 용도지역을 SQL로 재현 → 2019+ 동등 게이트 | 운영 적재(D-051 전) · 원본 삭제 · 전 기간 604,422를 게이트로 쓰는 것 |

테이블은 항상 전국 스키마(PNU PK)다. 파일럿은 **넣는 행만** 대전·충북이다. 화면을 특정 시도로 잠그지 않는 이유: 속성이 이미 전국이라 청주·유성구를 눌러 보는 것이 곧 검토이고, 잠그면 나중에 푸는 작업이 생긴다.

## 9. 하지 않는 것

범위를 좁게 잡는 것이 이 제안의 핵심이다.

| 안 함 | 이유 |
|---|---|
| **전국 3,900만 필지 전체** | 수요 필지만. 「건물 있는 595만」 전량 선적재도 목표가 아니다 |
| **소유자 정보** | 제품 요구 없음. 개인정보 취급 부담만 늘어난다 |
| **분할·합병 계보 (SCD Type 2)** | 「3~5년 뒤 완벽한 매칭」의 재료지만 지금 필요 없다. `first_seen`/`last_seen` 으로 최소 이력만. 확정 매칭 값 변경은 새 버전 행+명시 승인이지 `is_current` 자동 전환이 아니다 |
| **전유부 (호별 대장)** | 집합 통계 단위는 건물·단지다. 호별은 데이터가 수십 GB이고 쓸 곳이 없다 |
| **VPS 적재** | §4 |
| **분양권 블록-로트 지번 보강** | 원천에 지번이 없다(19.5%). 매칭 실패가 아니라 대상 외 |
| **집합 `building_key` 체계 교체** | PNU를 **덧붙일** 뿐 키를 갈지 않는다. 필지와 키가 거의 1:1이라 그럴 이유도 없다 |
| **연속 match_score** | 발명 점수(0.82) 금지. 복합 A1/A2, 집합 A–F/P/T |
| **`land_stats`를 `parcel_master`에 흡수** | 도메인 DB는 물리 분리. 기본통계 마트는 MOLIT-only |
| **확정 행 자동 rematch / `is_current` flip** | 동결은 `ON CONFLICT DO NOTHING`. 값 변경은 승인 |

## 10. 미결정

- ~~현행 지역지구구역 대장 확보 가능 여부~~ — **해결(부정)**. §6.3. `parcel_zone` 전국 적재는 §8.4에서 집합 필지 기준 완료(원본 48GB는 DB에 넣지 않음).
- **`parcel_master` DB 물리 위치** — 로컬 전용 확정. 현재 `building` 1,881,261 · `parcel` 366,838 (집합 전국). 파일럿 88,773은 §8.3.
