## 1. 결론 먼저

**필지(PNU)를 바탕에 두고 그 위에 건물을 얹는 구조가 맞다.** 추측이 아니라 원본이 그렇게 생겼다 — 우리가 쓰는 여섯 개 원본이 **전부** 법정동코드 + 본번 + 부번을 갖고 있고, K-apt는 아예 필지고유번호를 직접 준다(§2).

그런데 제안의 핵심은 스키마가 아니라 **이 DB를 어디에 두느냐**다. 결론은 **운영 서버에 올리지 않는다.** 축약대장은 제품이 조회하는 DB가 아니라 **값을 만들어내는 재료**다. 로컬에서 만들고, 결과 컬럼만 도메인 DB에 실어 보낸다(§4). 이건 VPS가 4GB RAM / 80GB SSD라는 제약에서 나온 타협이 아니라, 이미 `region_codes` 를 그렇게 쓰고 있는 기존 패턴과 같은 철학이다.

그리고 측정 과정에서 **복합과 집합의 난이도가 전혀 다르다**는 걸 확인했다. 복합은 지번이 마스킹돼 있어 확률적 매칭이고 정확도 인증이 필요하다. 집합은 **지번이 100% 온전해서 결정론적 조인**이다(§3). 그래서 집합부터 착수하는 것이 위험이 낮다.

## 2. 왜 필지가 자연 키인가

여섯 개 원본의 지역·지번 표현을 실제로 확인했다.

| 원본 | 필지 식별 방식 | 실측 |
|---|---|---|
| 건축물대장 표제부 `mart_djy_03.txt` | `[8]`시군구 + `[9]`법정동 + `[11]`본번 + `[12]`부번 | 806만 행 / **595만 필지** |
| 총괄표제부 `mart_djy_02.txt` | `[10]`+`[11]`+`[13]`+`[14]` | 62.1만 행 / 61.7만 필지 |
| 토지대장 `AL_D003` | `법정동코드` + `지번` | 충북·서울 확보 |
| 토지이용계획 `AL_D155` | `법정동코드` + `지번` | 충북·서울 확보 |
| 지역지구구역 `mart_shtreg_10.txt` | 시군구 + 법정동 + 본번 + 부번 | 303만 행 / **전국 17시도** |
| K-apt 단지 | **PNU 19자리 직접 제공** | 21,687단지 |
| 복합 실거래 | 마스킹 지번 → 복원 | 충북 81.5% · 서울 68.1% |
| 집합 실거래 | 지번 **마스킹 없음** | 아파트 99.7% 변환 가능 |

**K-apt가 결정적이다.** `20260814_단지_필지고유번호.xlsx` 는 「고유번호(19자리) ↔ 단지코드」 두 컬럼짜리 파일이고, 21,687단지 **전부**에 대해 PNU를 준다. 주 1회 갱신된다.

```
1111011800100720000  ←→  A11007001   (서울 종로구 내수동 72, 경희궁의아침3단지)
   └법정동10┘│└본번┘└부번┘
             └ 필지구분(1=토지, 2=산)
```

지금 우리는 K-apt를 **주소 문자열로** 매칭한다(`beopjungri_code` + 지번 파싱, 또는 단지명). 그런데 K-apt 법정동주소는 깨져 있는 경우가 있다 — A10021295는 주소가 「서울특별시 종로구 내수동 73-」로 부번이 잘려 있는데 **PNU는 `...100730000` 으로 온전하다.** 문자열 파싱을 PNU 조회로 바꾸면 이 부류의 실패가 사라진다.

**PNU 개념이 지금 코드에 아예 없다.** 저장소 전역에서 `PNU` 문자열이 0건이고, 필지를 키로 하는 테이블도 없다. 필지는 `recover_address.py` 안에서 `(법정동코드, 본번, 부번)` 튜플과 `_cache/*.json` 으로만 존재한다. 매번 3.5GB를 다시 훑는 이유가 이것이다.

## 3. 결정적 차이 — 집합은 매칭이 필요 없다

복합 데이터 보강이 어려웠던 이유는 전부 마스킹 때문이었다. 집합은 그 문제가 없다. 실측했다.

| 집합 유형 | 거래 | 지번 마스킹 | PNU 변환 가능 | 필지 | `building_key` |
|---|---|---|---|---|---|
| 아파트 | 4,495,834 | **0.0%** | **99.7%** | 43,354 | 45,743 |
| 연립·다세대 | 1,102,907 | **0.0%** | **99.9%** | 206,023 | 200,923 |
| 오피스텔 | 348,312 | **0.0%** | **100.0%** | 13,776 | 13,522 |
| 분양권 | 537,143 | 0.0% | 80.5% | 5,156 | 5,785 |

두 가지를 읽어야 한다.

**첫째, 집합 보강에는 「매칭 정확도」라는 개념이 없다.** 지번이 그대로 있으니 PNU를 만들어 조회하면 끝이다. 복합에서 우리를 괴롭힌 판별력·혼입·스냅샷 충돌이 전부 해당 없다. 인증 문턱을 세울 필요도 없다. 남는 건 **커버리지**뿐이고, 그건 대장에 그 필지가 있느냐의 문제다.

**둘째, `building_key` 와 필지가 거의 1:1이다.** 아파트 45,743개 키에 필지 43,354개다. 즉 PNU를 `building_key` 에 붙이는 것이 자연스럽고, 기존 키 체계를 갈아엎을 필요가 없다.

분양권 80.5%는 예외다. 나머지는 `BL-1`·`BL-A2` 같은 **블록-로트 표기**로, 지번이 아직 확정되지 않은 신규 택지다. 이건 매칭 실패가 아니라 **원천에 지번이 없는 것**이므로 보강 대상에서 제외한다.

## 4. 이 DB는 운영 서버에 올리지 않는다

가장 중요한 설계 결정이다.

### 지금의 구조

배치는 **로컬 PC에서** 돌리고, 검증 후 `pg_dump` 로 VPS에 promote한다. VPS는 Lightsail 4GB RAM / 80GB SSD이고 `land_stats` 하나가 이미 약 7GB다. 도메인 DB는 물리적으로 분리돼 있어(`land_stats` / `built_stats` / `collective_stats` / `rent_stats`) DB를 넘는 조인이 애초에 안 된다. 그래서 `region_codes` 는 **네 DB에 각각 복사본**으로 들어가 있다.

### 그래서 축약대장의 위치

축약대장은 **로컬 전용 다섯 번째 DB**(`parcel_master`)로 둔다. VPS에 올리지 않는다.

```
로컬 (배치 전용)                         VPS (운영)
┌────────────────────────┐
│ parcel_master          │
│  parcel · parcel_zone  │   매칭·조인
│  building · danji      │   ────────┐
└────────────────────────┘           │
                                     ▼
                        ┌────────────────────────────┐
   promote (pg_dump)    │ built_stats                │
   ◄────────────────────│  built_transaction_        │
                        │    enrichment              │
                        ├────────────────────────────┤
                        │ collective_stats           │
                        │  collective_building_      │
                        │    attributes (+pnu)       │
                        └────────────────────────────┘
```

이유가 세 개다.

**사용자가 조회하는 것은 필지가 아니라 거래다.** 거래목록에서 구조·용도지역을 보여주려면 「이 거래의 구조는 철근콘크리트」라는 **결과**만 있으면 된다. 그 결과를 만들기 위해 595만 필지를 훑는 일은 빌드 타임에 끝난다. 운영 서버가 필지 테이블을 가질 이유가 없다.

**용량이 맞지 않는다.** `parcel` 595만 행 + `building` 806만 행 × 3스냅샷 + `parcel_zone` 을 인덱스까지 얹으면 수 GB다. VPS 여유가 25GB 남짓인데 여기에 쓸 값이 없다.

**동결 정책과 맞물린다.** D-047이 정한 대로 확정된 보강 행은 **동결**한다. 그러면 운영 DB의 보강 값은 한 번 정해지고 안 바뀐다. 재계산 재료를 운영 서버에 둘 필요가 없다는 뜻이다.

## 5. 스키마 제안 — 4개 테이블

### 5.1 `parcel` — 필지

건물이 있는 필지만. 전국 3,900만 필지 전체를 넣지 않는다(§9).

| 컬럼 | 비고 |
|---|---|
| `pnu` CHAR(19) **PK** | 법정동10 + 필지구분1 + 본번4 + 부번4 |
| `beopjungri_code` CHAR(10) · `bun` CHAR(4) · `ji` CHAR(4) | 조인·조회용 분해 컬럼 |
| `sido_code` CHAR(2) · `sigungu_code` CHAR(5) | 지역 필터 |
| `jimok_code` CHAR(2) | 토지대장. 미확보 시도는 NULL |
| `land_area` NUMERIC | 토지대장 우선, 없으면 대장 대지면적 |
| `land_area_source` VARCHAR | `land_ledger` / `title` / `summary` |
| `first_seen` · `last_seen` | 스냅샷 범위 |

### 5.2 `parcel_zone` — 용도지역 (복수 라벨)

D-047이 정한 대로 단일 컬럼이 아니라 **행 단위 복수 라벨**이다. 필지가 두 용도지역에 걸치는 경우가 충북 8.7%·서울 9.4%다.

| 컬럼 | 비고 |
|---|---|
| `pnu` CHAR(19) · `zone_label` VARCHAR **PK(둘)** | |
| `zone_family` VARCHAR | 주거 / 상업 / 공업 / 녹지 / 관리 / 농림 / 자연환경 |
| **`is_coarse` BOOLEAN** | 「도시지역」·「관리지역」 등 상위 분류 여부 |
| `source` VARCHAR | `al_d155` / `shtreg` |
| `snapshot` VARCHAR | |

**`is_coarse` 는 어제 잡은 버그의 직접적 산물이다.** AL_D155의 대분류 라벨(「도시지역」)을 코드로 걸러내려 했는데 코드 체계가 시군구 단위로 달라 서울 34.2%·충북 0.4%가 샜다([`BUILT_DATA_ENRICHMENT.md`](BUILT_DATA_ENRICHMENT.md) §6 말미). 대분류를 **버리지 않고 플래그로 표시**하면 조회 쪽이 `WHERE NOT is_coarse` 한 줄로 안전해지고, 검증로봇의 「채운 값이 상위 분류면 실패」 규칙이 SQL 한 줄이 된다. 판정 로직이 파이프라인 안쪽에 숨지 않는다.

### 5.3 `building` — 건물 (동 단위)

| 컬럼 | 원본 | 비고 |

### 5.4 `danji` — K-apt 단지

**시공사의 유일한 출처다.** 건축물대장 표제부에는 시공사가 없다(77개 컬럼 전수 확인).

| 세대수 | **100.0%** |

## 6. 무엇이 채워지는가

### 6.1 복합 — 이미 인증된 경로

충북 81.5% · 서울 68.1%의 거래에서 지번이 확정되고 구조·용도지역이 동시에 채워진다. 축약대장이 바꾸는 것은 **정확도가 아니라 실행 방식**이다. 지금은 매칭 한 번에 3.5GB를 훑고 서울 3스냅샷이 14분 걸린다. `parcel` + `building` 이 DB에 있으면 SQL 조인이 되고, 원본 11.3GB를 지울 수 있다.

### 6.2 집합 — K-apt와 표제부가 상보적이다

집합 지역회귀([`D-045`](lab/decisions/D-045.json))가 필요한 변수는 세대수·층수·연식·구조·용도지역·시공사다. 두 원본의 역할이 다르다.

| 변수 | K-apt (21,687단지) | 표제부 `집합` (65.9만 동) |
|---|---|---|
| 시공사 | **유일 출처** 100% | 없음 |
| 세대수 | 100% | 72.3% |
| 최고층수 | 100% | 있음 |
| 구조 | 97.5% | 있음 |
| 사용승인일 | 100% | 있음 |
| 주차·난방·복도유형 | 있음 | 없음 |
| **연립·다세대·오피스텔** | **거의 없음** | **있음** |

K-apt는 **의무관리대상 공동주택**만이다. 아파트 `building_key` 45,743개에 K-apt 단지는 21,687개 — 절반이 비어 있고, 연립·다세대 200,923개와 오피스텔 13,522개는 사실상 전부 비어 있다. 현재 속성 커버리지가 단지 기준 58%에 머무는 이유다.

**표제부 `집합` 65.9만 동이 그 빈칸을 메운다.** 시공사는 못 채우지만 세대수·층수·구조·승인일은 채운다. 그러면 지역회귀에서 「시공사 없이 규모·연식·구조만으로 돌리는」 경우의 표본이 크게 늘어난다.

주용도 분포(표제부 `집합`)를 보면 아파트 계열 약 23.9만 동, 다세대 11.4만 동, 연립 2.0만 동이다. 연립·다세대 보강 폭이 가장 크다.

### 6.3 용도지역 — 전국 원천 후보를 찾았다

지금 용도지역은 AL_D155를 시도별로 받아야 하고 파일이 시도당 2.5GB다. 17개 시도면 40GB를 훑어야 한다.

`raw addition/기타/국토교통부_폐쇄말소대장_지역지구구역+(2026년+07월).zip` 을 열어 보니 **전국 17시도가 한 파일(411MB)에 들어 있고**, 결정적으로 구분 컬럼이 있다.

| 구분 | 행 |
|---|---|
| **용도지역코드** | 1,436,292 |
| 용도지구코드 | 835,884 |
| 용도구역코드 | 760,013 |

**AL_D155에서 우리를 물었던 문제가 원천에서 해결된다.** 용도지역·용도지구·용도구역이 뒤섞여 있어 코드 정규식(`^UQ[ABCD]`)으로 골라내야 했고, 대분류 강등을 코드로 판정하다 버그가 났다. 이 원장은 구분이 명시적이라 `WHERE 구분='용도지역코드'` 로 끝난다.

**단, 이 파일은 「폐쇄말소」 이력본이다.** 라벨에 「준농림지역」(51,662) 같은 2003년 국토계획법 이전 제도가 섞여 있다. 현행 필지 상태가 아니다. 그러므로 **현행판 지역지구구역 대장을 확보할 수 있는지가 선결 과제**다(§10). 확보되면 AL_D155 수집이 불필요해진다.

### 6.4 전국 확장 걸림돌 하나 해소

미해결로 남겨뒀던 시군구코드 문제를 확인했다. 표제부 2026-07의 시도코드 분포는 통합 신코드를 쓴다 — `12`(전남광주통합특별시) **928,704행**, `51`(강원특별) 477,226, `52`(전북특별) 513,966이고 구코드 `29`·`42`·`45`는 0건, `46`은 13건만 남아 있다. `built_transactions` 의 sido `12` 와 정합한다. **코드 불일치로 23%를 잃는 시나리오는 발생하지 않는다.**

## 7. 업데이트 정책

원본마다 갱신 주기가 다르므로 다운로드 주기도 달라야 한다. 근거는 D-047 실측이다.

| 원본 | 원천 갱신 | 우리 다운로드 | 근거 |
|---|---|---|---|
| 실거래 (MOLIT) | 월 | **월** (현행 유지) | 제품 본체 |
| K-apt 기본정보 + 필지고유번호 | 주 1회 | **월 1회** | 11MB로 가볍고 시공사 유일 출처 |
| 건축물대장 표제부·총괄 | 월 | **분기 1회** | 22개월 차이가 매칭률 1.4%p, 월 단위 0.1%p 미만 |
| 지역지구구역 / AL_D155 | 월 / 부정기 | **연 1회** | 용도지역 변경 잔차 0.3~0.4% |
| 토지대장 AL_D003 | 부정기 | **연 1회** | 대지면적 tie-break 전용 |

### 월간 배치에 추가되는 것

현행 순서는 `run_land_cycle_csv` → `run_built_cycle_csv` → `run_collective_cycle_csv` 이고, 각 도메인이 최근 12개 계약월을 purge하고 재적재한다. 여기에 한 단계를 붙인다.

```
1. 실거래 purge + 재적재            (현행)
2. 마트 빌드                        (현행)
3. enrich  ← 추가
     복합: 신규·정정 거래만 매칭. 확정 행은 동결.
     집합: 신규 building_key 만 PNU 조인.
4. 스냅샷 · 검증                    (현행)
```

**복합의 「확정 행 동결」은 타협이 아니라 요구사항이다.** 스냅샷마다 매칭 결과가 다르다는 것이 D-047 §7의 실측이다. 매월 재매칭하면 지난달 벽돌구조가 이번달 철골구조로 바뀔 수 있고, 그건 오류율보다 심각한 신뢰 파괴다. 대신 **미상 행은 새 대장이 올 때마다 재시도해도 안전하다** — 빈칸이 채워지는 방향은 개선으로만 보인다.

**집합은 동결이 필요 없다.** 결정론적 조인이라 같은 지번이면 항상 같은 PNU이고 값이 흔들리지 않는다. 오히려 지금의 `building_key`(주소+단지명 해시)보다 PNU가 안정적이다 — 원장 표기가 바뀌면 해시는 바뀌지만 PNU는 안 바뀐다.

### 원본 파일을 지울 수 있게 된다

지금은 매칭을 위해 `raw addition` 11.3GB를 계속 들고 있어야 한다. `parcel` + `building` + `parcel_zone` 이 적재되면 원본은 다음 분기 스냅샷을 받을 때까지 불필요하다. **적재 후 원본 삭제**를 정책으로 명시한다.

## 8. 착수 순서 — 집합이 먼저다

기존 문서들은 복합을 먼저 두고 있었지만, 실측 결과 순서를 바꾸는 것이 맞다. **집합이 결정론적이라 위험이 낮고, 지역회귀라는 대기 중인 제품 요구가 있다.**

| 단계 | 내용 | 완료 조건 |
|---|---|---|
| **0** | 복합 구조 표본 150건 사람 감사 | 복합 착수의 선행 조건 (진행 중) |
| **1** | `parcel` + `building` 적재 (표제부 3스냅샷 + 총괄) | 595만 필지 · 806만 동 × 3, `(pnu)` self-join 무결 |
| **2** | `builder_master` 에 `pnu` 추가 + K-apt 필지고유번호 적재 | 기존 주소 매칭과 **대조** — PNU 조인이 더 많이 맞는지 측정 |
| **3** | 집합 결정론적 조인 커버리지 측정 | `building_key` ↔ PNU ↔ `building`/`danji`. 유형별 채움률 리포트 |
| **4** | 복합 enrichment 파이프라인 | D-047 스키마 (`transaction_hash` PK) |
| **5** | 현행 지역지구구역 확보 시도 | 되면 `parcel_zone` 전국화, AL_D155 대체 |

**2단계가 검증 관문이다.** PNU 조인 결과를 기존 주소 매칭 결과와 대조해서, 늘어난 매칭이 실제로 옳은지 확인한 뒤에만 3단계로 간다. 여기서 「PNU가 가리키는 단지와 주소 매칭이 가리키는 단지가 다른」 건이 나오면 그게 신호다.

## 9. 하지 않는 것

범위를 좁게 잡는 것이 이 제안의 핵심이다.

| 안 함 | 이유 |
|---|---|
| **전국 3,900만 필지 전체** | 건물 있는 595만 필지만. 나머지는 제품이 쓰지 않는다 |
| **소유자 정보** | 제품 요구 없음. 개인정보 취급 부담만 늘어난다 |
| **분할·합병 계보 (SCD Type 2)** | 「3~5년 뒤 완벽한 매칭」의 재료지만 지금 필요 없다. `first_seen`/`last_seen` 으로 최소 이력만 |
| **전유부 (호별 대장)** | 집합 통계 단위는 건물·단지다. 호별은 데이터가 수십 GB이고 쓸 곳이 없다 |
| **VPS 적재** | §4 |
| **분양권 블록-로트 지번 보강** | 원천에 지번이 없다(19.5%). 매칭 실패가 아니라 대상 외 |
| **집합 `building_key` 체계 교체** | PNU를 **덧붙일** 뿐 키를 갈지 않는다. 필지와 키가 거의 1:1이라 그럴 이유도 없다 |

## 10. 미결정

- **현행 지역지구구역 대장 확보 가능 여부** — 지금 있는 건 폐쇄말소 이력본이다. 현행판이 건축HUB에서 제공되는지 확인해야 하고, 안 되면 AL_D155 시도별 수집(17 × 2.5GB)을 계속해야 한다. §6.3의 이점이 여기에 걸려 있다
- **`parcel_master` DB 물리 위치** — 로컬 전용은 확정. 별도 DB(`parcel_master`)로 둘지, `built_stats` 안의 별도 스키마로 둘지는 적재 실험 후 결정
- **집합 표제부 매칭 규칙** — 집합 실거래는 지번이 온전하지만 **동(棟) 식별**은 별개다. 한 필지에 여러 동이 있을 때 어느 동을 `building_key` 에 붙일지(단지 대표값 / 동별 분리 / 세대수 가중)는 3단계에서 측정하고 정한다
- **`households` 컬럼 정체 확인** — 표제부 `[40]` 을 세대수로 읽었다(롯데캐슬 로잔 101동 37, 숭인상가아파트 246). K-apt 세대수와 교차 검증해서 확정할 것
- **적재 소요·용량 실측** — 인덱스 포함 크기와 로컬 적재 시간. 1단계에서 나온다
- 표제부 시도코드 이상치 — `99`(969행) · `38`(1행) · `0`(1행) · `46`(13행). 소수이지만 적재 시 격리 규칙 필요

## 11. 한 줄

**필지(PNU)를 바탕에 두고 건물을 얹는 구조가 맞다** — 여섯 개 원본이 모두 법정동+본번+부번을 갖고 K-apt는 PNU를 직접 주기 때문이다. 다만 이 DB는 **로컬 빌드 타임 자산**으로 두고 운영 서버에는 결과 컬럼만 보낸다. 그리고 **집합을 먼저 한다** — 집합 실거래는 지번 마스킹이 0%라 결정론적 조인이고, K-apt가 못 덮는 연립·다세대 20만 건물을 표제부가 메워 지역회귀의 표본을 늘린다. 복합은 구조 표본 감사가 끝난 뒤 같은 필지 테이블 위에서 SQL 조인으로 바뀐다.
