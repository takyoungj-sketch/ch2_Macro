## 0. 요약

목표는 집합 통계를 "건물별 거래통계"에서 **"단지 가치분석"**으로 확장하는 것이다. 시공사·브랜드·단지규모를 붙여 ① 신규·분양단지의 예상 입주시세, ② 지역·면적·연식·규모를 통제한 **브랜드 프리미엄**을 산출하는 구상이다.

**결론: 방향은 타당하고, 데이터 근거는 기존 문서 추정보다 훨씬 좋다. 단, 3가지 구조적 제약이 있어 스코프를 조정해야 한다.**

| 구상 | 실측 판정 | 근거 |
|---|---|---|
| 시공사·구조·규모 보강 | **가능 — 거래 기준 82.6% 커버** | K-apt 매칭 tier A+B+C, 승인연도 교차검증 96~98% 일치 |
| 규모효과(세대수·동수·주차) | **가능** | 세대수 중위 438세대, p10~p90 158~1,118 — 분산 충분 |
| 브랜드 프리미엄 | **가능하나 새 모형 계층 필요** | 현재 회귀는 단지 FE 사용 → 브랜드가 FE에 흡수돼 **식별 불가** |
| 신규 분양단지 예상 입주시세 | **부분 가능 — 특성 입력이 별도 필요** | K-apt는 **준공 후** 등록. 분양중 단지 특성은 원천에 없음 |
| 「분양가 → 입주시세」 학습 | **분양가 없음 → 스코프 조정 필요** | MOLIT 분양권은 **전매 거래가**(프리미엄 포함), 분양가 컬럼 자체가 없음 |

가장 중요한 발견은 두 가지다.

1. **아파트 실거래는 지번이 마스킹되지 않는다.** 따라서 `법정동코드 + 지번` 매칭이 가능하고, 이 경로가 단지명 매칭의 결측을 대부분 메운다. 기존 문서의 매칭률 추정(57~71%)은 이름 매칭만 본 값이라 **과소평가**였다.
2. **브랜드 프리미엄은 데이터 문제가 아니라 모형 계층 문제다.** 지금의 단지 FE 회귀에 브랜드 더미를 추가하면 완전공선이 되어 계수가 나오지 않는다. 2단계 회귀(단지 FE 추정 → FE를 단지특성에 회귀)로 풀어야 하며, 이 방식은 **기존 엔진을 수정하지 않고** 위에 얹을 수 있다.

### 1.1 K-apt 단지 매칭 — 지번 경로가 결정적

### 1.3 브랜드 — 시공사와 분리해야 하는 이유가 데이터로 확인됨

- **K-apt에 브랜드 컬럼이 없다.** 브랜드는 단지명에서 추출해야 한다.
- 주요 브랜드 25종 사전으로 시험 추출: **단지 3,891개(9.3%) / 거래 622,498건(18.7%)** 커버. 브랜드가 없는 단지(구축·주공·지역 건설사)가 다수여서 이 정도가 정상이다 — 브랜드 프리미엄은 브랜드 단지 안에서만 정의되므로 한계가 아니다.
- **시공사 정규화가 필요하다.** 매칭된 18,866단지의 시공사는 원문 5,960종. 단순 정규화(법인 접미어·`건설/산업개발` 제거)로 3,492종까지 줄었지만, 이 단순 규칙은 **`현대건설`과 `현대산업개발`을 「현대」로 합쳐 버린다**(1,090단지) — 수작업 검증한 정규화 사전이 반드시 필요하다.
- 정규화 후 상위 20개 시공사가 매칭 거래의 30.3%, 상위 50개가 45.2%. **단지 30개 이상 그룹 117개, 거래 500건 이상 그룹 691개** → 상위 30~50개 더미 + 「기타」 구성이 현실적이다.

**식별성 확인:** 228개 시군구 중 **163개가 2개 이상 브랜드**, **141개가 3개 이상 브랜드 + 거래 300건 이상**, 시군구당 브랜드 종수 중위 **8개**. 즉 지역을 통제하고도 브랜드 더미를 추정할 수 있는 표본 구조다 — "A브랜드는 강남에만 공급돼서 비싸 보인다"는 교란을 실제로 걷어낼 수 있다.

### 1.4 분양권 ↔ 준공 연결 — 가능하지만 「분양가」는 없다

| 항목 | 값 |
|---|---|
| 분양권 단지 / 거래 | 4,085 / 374,971 |
| 준공 아파트 단지와 1:1 연결(주소+정규화 단지명) | **2,249단지 (55.1%)** |
| 양쪽 모두 n≥5 (학습 가능) | **1,506단지** |
| 분양권 최초거래 → 아파트 최초거래 간격 | 중위 **1년** (p25~p75: 0~2년) |

연결 자체는 충분히 된다. 문제는 **가격의 성격**이다.

- MOLIT 분양·입주권 원장 스키마(`pipeline/collective/molit_schemas.py::PRESALE`)에는 `price`(거래금액)·`exclusive_area`·`floor`·`housing_subtype`만 있고 **`분양가`·`건축년도`·`동`이 없다**.
- 이 `price`는 최초 분양계약가가 아니라 **전매 거래가(프리미엄 포함)**다. 간격 중위 1년도 그 때문이다(전매가 준공 직전에 활발).
- 따라서 구상 ⑤의 "분양가 6.5억 → 입주 후 7.4억" 형태는 **현재 보유 데이터로 불가**하다. 분양가는 청약홈(APT 분양정보)·HUG(민간아파트 분양가격 동향, 지역 평균)·부동산원 등 **외부 원천을 새로 확보**해야 한다.
- 대신 **"분양권 시세 → 입주 후 실거래가"** 관계는 1,506단지로 지금 바로 학습 가능하다. 사용자 가치는 상당 부분 살아남는다("현재 프리미엄 수준이면 입주 시점 시세는 어느 구간인가").

| 규모 | 단지 수 |
|---|---|

## 2. 구조적 제약 — 스코프에 반드시 반영할 것

### 2.1 단지 FE와 단지특성은 동시에 추정할 수 없다 (가장 중요)

현재 집합 회귀(`backend/app/collective/regression/engine.py`)는 두 계층뿐이다.

- **건물 회귀**: 단일 `building_key` 내부 거래 → 설명변수 `전용면적·연식·층·동·권리구분`
- **코호트 회귀**: 여러 단지 pooling → **단지 고정효과(FE) 더미 자동 추가**(`cohort_mode`)

여기에 브랜드·세대수·구조·시공사를 넣으면 **단지 안에서 값이 변하지 않으므로 단지 FE와 완전공선**이 되어 계수가 소멸한다. 즉 "코호트 회귀에 브랜드 더미 옵션 추가"는 작동하지 않는다.

**권고: 2단계(two-step) 설계**

```
1단계  기존 코호트 회귀 그대로 사용
       ln(price) = 전용면적 + 연식 + 층 + 계약연도 + 단지 FE
       → 단지별 FE 추정치 = "이 단지의 통제 후 가격수준"

2단계  단지 FE(또는 단지 단위 품질지수)를 단지특성에 회귀
       단지FE = 지역 FE + log(세대수) + 구조 + 브랜드 + 시공사군 + 층수 + 주차대수/세대 + ε
       → 브랜드 계수 = 브랜드 프리미엄
```

> **설계 확정안:** [`COLLECTIVE_TWO_STAGE_HEDONIC_DESIGN.md`](COLLECTIVE_TWO_STAGE_HEDONIC_DESIGN.md)
> (표본 규칙·DDL·API·검증 기준까지 구현 SSOT로 확정. 2026-08-09)

이 방식의 장점:

- **기존 엔진·API를 수정하지 않는다**(신규 변수 블록을 넣지 않으므로 회귀 결과 재현성 유지).
- 단지 특성은 단지 1개 = 관측 1개로 들어가므로 **표본 단위가 정직하다**. 거래 단위로 브랜드 더미를 추정하면 같은 단지 거래가 수백 건 복제되어 t값이 과대평가된다(단지 단위 클러스터 표준오차 없이는 필연). 2단계는 이 문제를 구조적으로 회피한다.
- 지역 FE 수준(시군구/읍면동)을 2단계에서 자유롭게 바꿔 볼 수 있다.

### 2.2 분양중(미준공) 단지의 특성은 어디에도 없다

K-apt는 **관리주체 등록 기반**이므로 사용승인 이후에만 데이터가 생긴다(수록 최대 2026년 승인, 2025년 이후 승인 515단지). 따라서 "지금 분양 중인 단지"의 세대수·동수·주차·브랜드는 K-apt로 채울 수 없다. 선택지는 둘이다.

1. **사용자 입력 폼** — 위치·전용면적·세대수·층수·브랜드·입주예정을 사용자가 넣고 모형이 예상 시세를 반환(시나리오 계산기). 외부 데이터 없이 즉시 가능.
2. **청약홈 분양정보 연계** — 분양단지 마스터를 자동 수집(분양가까지 확보 가능). 별도 원천 확보·약관 검토 필요.

**권고: 1단계로 입력 폼 방식(P5), 청약홈 연계는 별도 트랙**으로 분리한다.

### 2.3 단지 특성은 「현재 스냅샷」이다

K-apt는 주 1회 갱신 스냅샷이며 시점 이력이 없다. 과거 거래에 현재 특성을 붙이는 형태가 되는데, 세대수·구조·시공사는 사실상 불변이라 큰 문제는 없다. 다만 **리모델링·증축·주차 증설·단지 통합**은 예외이므로 `attr_snapshot_ym`을 함께 저장해 재현성을 확보해야 한다. CH2는 월간 배치이므로 **월 1회 스냅샷 고정** 정책이 맞다.

## 3. 데이터 구조 권고 — 원자료 보존, 분석변수 분리

구상 4번(시공사 ≠ 브랜드)은 실측으로도 뒷받침된다(시공사 원문 5,960종, 공동시공·법인 표기 혼재, 브랜드는 별도 원천 없음). 따라서 **원자료 컬럼과 분석용 파생 컬럼을 분리**한다.

```
builder_master              (K-apt 스냅샷 원본 보존, 단지코드 grain)
  단지코드 · 단지명 · 법정동주소 · 도로명주소 · 사용승인일
  시공사(원문) · 시행사(원문) · 건물구조(원문) · 세대수 · 분양세대수 · 임대세대수
  동수 · 최고층수 · 지하층수 · 총주차대수 · 단지분류 · 분양형태 · snapshot_ym

collective_building_attributes   (building_key grain — 매칭 결과)
  building_key · 단지코드 · match_tier(A/B/C/E) · match_confidence
  builder_raw · builder_norm · builder_group      -- 시공사(원문/정규화/그룹)
  developer_raw · developer_norm                  -- 시행사
  brand · brand_source(name_parse|manual)         -- 브랜드(단지명 파생)
  structure_group(RC/SRC/기타) · households · households_sale · households_rent
  dong_count · max_floor · parking_total · parking_per_household
  danji_class · supply_type · approved_date · attr_snapshot_ym
```

- `builder_norm`(표기 정규화)과 `builder_group`(기업집단 단위)을 **분리**한다 — 현대건설/현대엔지니어링/현대산업개발을 합칠지는 분석 목적에 따라 달라진다.
- 브랜드 사전은 `brand ↔ builder_group` **다대다 매핑표**로 별도 관리한다(한 시공사 여러 브랜드, 공동시공 존재).
- 공동시공은 원문을 그대로 두고 `builder_group`을 다중값 또는 대표사 + `is_joint` 플래그로 표현한다.

## 4. 단계별 계획(안)

| 단계 | 내용 | 산출 | 선행 | 공수(초안) |
|---|---|---|---|---|
| **P1** | K-apt → `builder_master` 적재 + `법정동코드+지번/단지명` 매칭 → `collective_building_attributes` | 단지 속성 테이블, 매칭률 리포트 | `apt_mst_info` 출처 확인 | 3~4일 |
| **P2** | 시공사 정규화 사전 + 브랜드 사전 + 브랜드↔시공사 매핑 | `builder_norm/group`, `brand` | P1 | 2~3일(수작업 검증 포함) |
| **P2.5** | **단지 상세 모달에 단지 정보 표시**(세대수·동수·구조·시공사·주차·분양형태) | 즉시 체감되는 UI 가치, 회귀 변경 없음 | P1 | 1~2일 |
| **P3** | **2단계 회귀 엔진** — 1단계 단지 FE(기존 엔진 재사용) → 2단계 단지특성 회귀(지역 FE + 규모 + 구조 + 브랜드) | 신규 API 1개, 기존 회귀 불변 | P2 | 4~6일 |
| **P4** | **브랜드 프리미엄 리포트** — 통제 후 계수·CI·표본수, 전국/시도/시군구 단위 | 구상 ⑤ | P3 | 2~3일 |
| **P5** | **신규·분양단지 예상 시세** — 입력 폼 기반 시나리오 예측(점추정 + 예측구간 + 유사단지 대비 %) | 구상 ④ | P3 | 3~5일 |
| **P6** | **단지 가치분석 종합 화면** — 추정가/지역 대비/규모효과/브랜드 프리미엄/유사단지 | 구상 ⑥ | P4·P5 | 3~4일 |
| **별도** | 분양가 원천 확보(청약홈·HUG) → 「분양가 → 입주시세 상승률」 | 구상 ⑤ 완전판 | 외부 데이터 | 미정 |

합계 **약 16~24 작업일**(분양가 트랙 제외). P1·P2.5까지만 해도 "단지 정보가 보인다"는 가시적 가치가 생기고, 회귀 관련 리스크는 P3부터 시작된다 — **P1 → P2.5 → 중간 점검** 순서를 권고한다.

### 결과 표현 원칙

구상에서 제시한 표현 방식을 그대로 채택한다(단일 숫자 금지).

```
예상 시세      7.8억
예상 범위      7.4 ~ 8.2억   (예측구간, 모형 MAPE 병기)
지역 내 유사단지 대비  +4.3%
브랜드 프리미엄  +4.7%  (n=단지 수, p값, 통제변수 명시)
```

브랜드 프리미엄은 **"동일 지역·면적·연식·규모를 통제했을 때의 추가 기여"**라는 정의문을 UI에 항상 병기한다 — 단순 평균가격과 혼동되면 제품 신뢰가 깨진다.

**CH2 Macro는 AVM이 아니다.** 위 숫자들은 "정답"이 아니라 사용자가 변수·표본·모형 스펙을 직접 바꿔가며 검증하는 **탐색 대상**이다. 따라서 P3~P6은 결과값과 함께 방정식·계수표·기준범주·표본 포함/제외 내역·기여도 분해를 항상 노출한다. 상세 규칙: [`COLLECTIVE_TWO_STAGE_HEDONIC_DESIGN.md`](COLLECTIVE_TWO_STAGE_HEDONIC_DESIGN.md) §0.1·§6.2.

## 6. 주거·비주거 parity 예외

`AGENTS.md`·`.cursor/rules/collective-residential-commercial-parity.mdc`는 집합 작업을 주거·비주거 동시 진행으로 규정한다. **이 트랙은 예외**다 — K-apt는 공동주택 관리 데이터라 비주거 집합(도로명 cluster)에는 대응 원천이 없다. 통계 방식·UI 골격의 동일성 원칙은 유지하되, **단지 속성·브랜드 프리미엄은 주거 전용 기능**으로 문서화한다. 비주거의 대응 항목(구조·연식 등)은 건축물대장 트랙(보류)에 묶여 있다.
