## 0. 배경 — 왜 다시 조사하는가

CH2 Macro의 근본 한계는 **국토부 실거래가 단일 원천**이다. 이 원천은:

- **번지 마스킹** (`5**`, `7**`, `1***` 등) — 특정 조건에서 지번의 일부만 공개
- **자산유형별 원본 컬럼 자체가 다름** — 예: 상업업무·공장창고 파일에는 `용도지역`이 있지만 **단독다가구 파일에는 처음부터 이 컬럼이 없음** (원천 결측, 마스킹이 아니라 **미제공**)
- **구조·시공사·브랜드 등 건물 특성 변수가 전혀 없음**

2026-06 조사([`BUILDING_REGISTER_ROADMAP.md`](BUILDING_REGISTER_ROADMAP.md))는 건축물대장 표제부로 복합 구조 변수를 보강하려 했으나, 지번 마스킹 때문에 **확정(tier A/B) 매칭률이 11%**에 불과했다 — 사용자가 "예전에 다른 에이전트와 매칭작업을 시도했었는데 큰 성과가 없었다"고 언급한 시도다.

이번 조사는 그 결론을 뒤집으려는 것이 아니라, `raw/raw addition/` 폴더에 새로 모인 자료 중 **마스킹의 영향을 덜 받는 종류의 데이터**가 있는지 실측으로 재평가한 것이다. **Phase 0 파일럿을 실제 DB(충북 detached 18,954건, 서울/전국 apartment 500건 표본)로 실행**해 아래 결론을 숫자로 확인했다(§2.1·§2.2):

> **집합(아파트) 시공사 데이터는 마스킹이 없어 텍스트 정규화만으로 실제 매칭률 57~71%가 나온다 — 착수 가치 높음. 단독다가구 용도지역 데이터는 지번 마스킹의 영향이 생각보다 커서(같은 법정동+마스킹 패턴 후보군 내 최빈 용도지역 적중률 62%, 완전 동질 6%) "확정" tier로 쓰기는 어렵고 "약한 확률적 신호"로 제한해야 한다. 건축물대장 구조 매칭은 기존 결론(11%, 보류)을 유지한다.**

## 2. 데이터별 상세 평가

### 2.1 K-apt 단지 기본정보 + `apt_mst_info` → 집합(아파트) **시공사·구조** — 우선순위 1위

**현재 상태 확인** (코드 실측, `backend/app/collective/schemas.py`·`engine.py`, `db/016_collective_transactions.sql`):

- 집합 OLS 회귀 설명변수는 `exclusive_area`, `building_age`, `floor`, `dong` 더미, `housing_subtype` 더미, (+ 단지 fixed effect)뿐이며 **시공사·구조 변수는 전혀 없다** (스텁도 없음).
- `collective_transactions`에는 `building_name`, `beopjungri_code`, `lot_number`, `road_name`, `building_year`가 이미 존재하고, `building_key`(`pipeline/collective/building_keys.py`)가 `asset_type|addr1-3|정규화된 단지명` 조합을 해싱해 건물을 식별한다. **`building_year`는 key에 포함되지 않음** — 별도 매칭 테이블로 붙여야 한다.

**신규 데이터 실측**:

- K-apt 단지 기본정보: 시공사("쌍용건설" 등), 시행사, 건물구조("철근콘크리트구조"), 최고층수, 세대수, 사용승인일, **법정동주소 평문**("서울특별시 종로구 내수동 72 경희궁의아침3단지"), 도로명주소, 단지코드(`A11007001` 형식).
- `apt_mst_info_202410.csv`: `cnst_entrprs_nm`(시공사명), `hus_mngm_entrprs_nm`(관리업체), `buld_stru`(구조), `legaldong_cd`(법정동코드), `lnno_adres`(지번주소 평문, 예 "서울특별시 종로구 낙원동 288번지" — **마스킹 없음**), `rdnmadr`(도로명주소), 위경도.
  - `apt_cd`(예 `APT1111021000010428000001`)는 코드 규칙이 불명확해(`legaldong_cd`와 불일치) 직접 파싱 키로 쓰지 않는다 — `legaldong_cd` + `lnno_adres` 정규화 매칭이 안전하다.
  - **출처가 문서에 명시되어 있지 않음** — 착수 전 파일 원출처(공공데이터포털 API명 등) 확인 필요(§5 리스크).

**매칭 확신도가 높은 이유**: 이 데이터는 **개인 거래가 아니라 단지(건물) 자체의 마스터 정보**이므로 원천적으로 마스킹 대상이 아니다. 집합 아파트는 이미 `building_name`(단지명)이 비마스킹 상태로 거래 원장에 들어 있으므로, "단지명 정규화 + 법정동/도로명 일치"라는 **기존에 이미 하고 있는 방식(building_key 정규화)을 그대로 재사용**해 조인하면 된다 — 건축물대장처럼 지번 하나로 좁혀야 하는 문제가 아니다.

**Phase 0 파일럿 실측 (2026-08-04, DB `collective_stats.collective_transactions`, `asset_type='apartment'` 500건 랜덤 표본 vs K-apt 21,651개 단지)**:

| 매칭 로직 | exact | exact+unique contains | 참고 후보 있음(다중 후보 포함) |
|---|---|---|---|
| 1차: `addr2`(시/군) 그대로 매칭 | 20.2% | 46.4% | 58.0% |
| 2차: `addr2+addr3` 결합 정규화 후(예 "고양시"+"덕양구"→"고양덕양구") | **23.8%** | **57.4%** | **71.0%** |

1차 시도에서 실패 원인의 상당수(88/500, 17.6%)가 **텍스트 포맷 차이**였다 — K-apt는 시군구를 `고양덕양구`·`고양일산동구`처럼 **붙여서** 표기하는데 CH2 `addr2`는 시(`고양시`)만 담고 구는 `addr3`에 따로 있다. 이 결합 로직만 추가해도 매칭률이 46→57%(고유 매칭), 58→71%(후보 있음)로 뛰었다 — **간단한 정규화 버그 수정만으로도 개선 여지가 크다는 뜻**. 남은 실패(28.0% no_match, 13.4% 후보 다수)는 K-apt 미가입 소규모 단지, 브랜드 표기 차이(예 "아이파크" vs "I-PARK" — `pipeline/collective/building_keys.py`의 기존 `_BRAND_ALIAS_PATTERNS` 재사용 여지), 세종시 등 특수 행정구역 케이스로 추정된다.

**예상 산출**: `builder_brand`(시공사 상위 N개 + 기타) 더미, `structure_name`(RC/철골/기타) 더미 — 회귀 설명변수로 추가. 실측 매칭률(exact+contains 57~71%)은 tier A/B만 회귀에 사용한다는 기존 원칙(§ `BUILDING_REGISTER_ROADMAP.md`)을 적용해도 실사용 가능한 수준.

**매칭률 갱신 (2026-08-09, 아파트 전량 41,832단지 / 332만 거래 실측)**: 위 57~71%는 **단지명 매칭만** 본 값이라 과소평가였다. **아파트 실거래는 지번이 마스킹되지 않으므로** `법정동코드 + 지번` exact 매칭이 가능하고(단지 30.1% / 거래 60.1%), 이름 매칭과 합치면 **거래 기준 82.6%(tier A+B+C)**, 부분일치 포함 **85.4%**까지 올라간다. K-apt 사용승인연도 vs `building_year` 교차검증에서 지번 tier는 96.1% 완전일치·98.3%가 ±1년으로 오탐이 낮다. 단지 기준(44.9%)이 낮은 이유는 미매칭이 거래가 거의 없는 소규모(비의무관리) 단지에 몰려 있기 때문이다. 상세: [`COLLECTIVE_RESIDENTIAL_VALUATION_EXPANSION_REVIEW.md`](COLLECTIVE_RESIDENTIAL_VALUATION_EXPANSION_REVIEW.md) §1.1.

### 2.2 AL_D155(용도지역지구, 충북) → 복합 단독다가구 **`zone_type`** — 우선순위 2위

**근본 원인 재확인** (`pipeline/built/molit_schemas.py` 실측):

```python
COMMERCIAL_FACTORY.columns = {..., "zone_type": 5, ...}   # 상업업무·공장창고엔 용도지역 있음
DETACHED.columns          = {..., "lot_number": 2, ...}   # 단독다가구엔 zone_type 자체가 없음
```

`built_transactions` DB 스키마에는 `zone_type` 컬럼 자체가 있지만(전 자산유형 공용), **단독다가구는 원천 MOLIT 파일에 이 컬럼이 없어 항상 결측**이다. 상가와 달리 "마스킹된 것"이 아니라 "처음부터 국토부가 이 파일 형식에 용도지역을 넣지 않는다"는 원천 설계 차이다. 이 때문에 상가·단독다가구 통합회귀에서 `zone_type_dummy` 블록을 켜면 단독다가구 표본이 통째로 빠지거나(`unified` 모드에서 detached zone은 null 처리) 변수 자체가 약해진다.

**실측 — 지번 마스킹 현황**: 단독다가구 raw 원본(`raw/raw base/단독다가구_2021_2026/강원특별자치도_단독다가구_매매_2024.csv`)을 직접 확인한 결과, 샘플 15건 **전부** 지번이 마스킹되어 있었다(`7**`, `9**`, `1***`, `8*` 등). 즉 **단독다가구도 상가와 동일하게 지번 마스킹 대상**이다 — 마스킹이 없다고 가정하면 안 된다.

**AL_D155 실측** (충북 43, 샘플 1만 행):

- `법정동코드`(10자리) + `지번` grain, `대장구분명`(토지대장/임야대장), `용도지역지구코드/명`. 한 필지에 여러 행(용도지역 + 용도지구 + 구역이 각각 별도 행)이 붙는 구조.
- **핵심 용도지역**(주거/상업/공업/녹지/관리/농림 등 21종 세부 분류)과 **용도지구·구역**(가축사육제한, 자연재해위험개선지구 등)이 같은 컬럼에 혼재 — 코드 접두어(`UQ*`=주거, `UC*`=상업 등 국토계획법 코드체계로 추정)로 구분 가능해 보이나 **공식 코드표 확보는 안 됨** (파일럿 착수 시 필요).
- **Phase 0 파일럿 실측 (2026-08-04, 실제 마스킹 폭 기준 재검증)**: 최초 조사에선 지번 앞 2자리만 잘라 동질성을 76%로 추정했는데, 이는 실제 마스킹보다 훨씬 세밀한(=낙관적인) 근사였다. 이번엔 **실제 DB의 마스킹 패턴을 그대로** 사용해 재검증했다:
  - `built_transactions`(충북 detached, 18,954건)에서 실제 마스킹 패턴 표본 확인 → `2**`(3자리 중 1자리만 노출), `8*`(2자리 중 1자리), `1***`(4자리 중 1자리) 등, **자릿수와 노출 폭이 지번마다 다르고 대부분 1자리만 노출**된다(2자리 노출인 내 첫 근사보다 실제로는 더 가혹함).
  - 충북 detached의 (법정동코드, 마스킹패턴) 조합 **5,251개** 전체에 대해, AL_D155 충북 전체 파일(1,490만 행 read, 용도지역 세부 21종만 필터링해 342만 행 추출)에서 **동일 자릿수 + 동일 노출 접두어**를 만족하는 실제 후보 필지를 모두 찾아 용도지역 다양성을 측정:
    - **완전 동질(후보 전부 동일 용도지역) 비율: 6.4%** (최초 근사 76%보다 훨씬 낮음)
    - **최빈 용도지역 다수결 시 예상 정확도(평균): 61.9%**
    - 후보군 크기(중앙값): **257개 필지** — 마스킹 폭이 넓어 후보군 자체가 매우 크다.
  - **해석**: "완전 확정" tier로는 쓸 수 없다(6%). 다만 다수결 정확도 62%는 21개 세부 용도지역 카테고리 기준 무작위 추측(~5%)보다는 훨씬 높고, 건축물대장 tier B(면적 조건 추가 시 2.8%)보다도 낫다 — **"약한 확률적 신호"(soft feature) 정도로는 쓸 수 있으나, hard 필터·확정 표시는 금물**이라는 것이 이번 실측의 결론이다.
- **스코프 문제**: 현재 보유본은 **충북(43)뿐**이며 파일 자체가 2.6GB — 전국 17개 시도로 확장하면 수십GB 규모가 될 것으로 추정된다.

**예상 산출**: 단독다가구 `zone_type`에 대한 **확률 벡터 또는 최빈값 참고 표시**(확정 아님) — 상가·단독다가구 통합회귀에서 용도지역 더미가 완전히 빠지는 것보다는 낫지만, "확정 tier" 언어는 쓰지 않는다.

### 2.3 건축물대장 3종(`mart_djy_01/02/03`) → 복합 **구조** — 기존 결론 유지(보류)

[`BUILDING_REGISTER_ROADMAP.md`](BUILDING_REGISTER_ROADMAP.md)의 2026-06 조사(표제부 804만 행, 충북 45.9만, `beopjungri+lot_prefix`만으로 후보 88%·확정 tier 11%, 면적 exact 조건 추가 시 2.8%로 급감)를 **재확인**한다. 이번에 실제로 파일 3종(기본개요·총괄표제부·표제부) 모두가 로컬에 존재함을 확인했지만:

- **컬럼 헤더가 없다** — `mart_djy_01`은 30열, `mart_djy_02`는 64열, `mart_djy_03`은 77열, 전부 숫자 인덱스 위치로만 구분되고 공식 레이아웃 스펙 문서가 폴더 내에 없다. 착수 시 국토교통부 공공데이터포털의 "건축물대장 표제부" 레이아웃 문서를 별도로 확보해야 컬럼을 확정할 수 있다.
- 근본적인 지번 마스킹 문제(§2.2에서 확인한 것과 동일한 마스킹이 상가·복합 거래에도 적용됨)는 그대로 유효하다.

**결론:** 이 데이터의 우선순위는 **2.1·2.2보다 낮음** — `BUILDING_REGISTER_ROADMAP.md`의 "구현 보류" 상태를 유지한다. 착수한다면 그 문서의 tier A/B/C/D 체계를 그대로 따른다.

### 2.4 상업용부동산 임대동향조사 — 회귀 변수 아님, Regional Profile 후보

한국부동산원 상권 단위 임대료·공실률·투자수익률 **집계** 통계(상권/지역 grain) — 개별 거래·건물에 매칭할 수 없다. 회귀 설명변수가 아니라 [`REGIONAL_PROFILE_POST_MVP_BACKLOG.md`](REGIONAL_PROFILE_POST_MVP_BACKLOG.md) 카탈로그 확장 후보(상권 macro 지표)로 별도 검토 대상이다. 이번 계획 범위에서는 제외.

### 2.5 아파트 전월세 실거래 — 낮은 우선순위

매매가 아닌 임대 거래(단지명 평문, 지번 대부분 비마스킹)라 매매 회귀에 직접 매칭할 대상이 아니다. 향후 "전월세가율" 등 파생 지표를 만들 때 참고할 수 있으나 이번 계획의 핵심은 아니다.

### Phase 0 — 파일럿 검증 ✅ 완료 (2026-08-04, DB 적재 없이 pandas + 실제 DB 조회로 실측)

- **0-B (AL_D155):** ✅ 완료. 실제 마스킹 폭 그대로(충북 detached 18,954건에서 추출한 실제 (법정동코드,마스킹패턴) 5,251개 조합) AL_D155 충북 전체(1,490만 행 스캔) 대비 재검증 — 완전동질 **6.4%**, 다수결 정확도 **61.9%**, 후보군 중앙값 **257개**. 최초의 76%(2자리 근사) 추정은 폐기. `UQ/UC/UI/UG/UZ/UA` 코드 접두어의 정식 의미는 여전히 미확인(용도지역 **이름** 문자열로 필터링해 우회했음 — 정식 코드표 확보는 Phase 2 착수 시 필요).

### Phase 1 — 집합 시공사 보강 (우선순위 1위, Phase 0 실측으로 착수 근거 확보)

1. `apt_mst_info_202410.csv` 출처 확인(§5) → 문제 없으면 K-apt 단지 기본정보(최신 스냅샷)를 `builder_master` 참조 테이블로 적재 (단지코드/단지명/법정동주소/시공사/구조/승인일).
2. `collective_transactions` ↔ `builder_master` 매칭 뷰 — **`addr2+addr3` 결합 정규화**(Phase 0에서 확인된 핵심 개선점) + 단지명 정규화(`normalize_building_name_for_key`의 브랜드 별칭표 재사용) + 세종시 등 단일 계층 행정구역 예외 처리.
3. 매칭 결과에 `builder_match_tier`(exact / unique-contains / multi-candidate) 부가, 회귀 엔진(`collective/regression/engine.py`)에 `builder_brand_dummy` 옵션 추가 — tier `multi-candidate`(13.4%)·`no_match`(28%)는 결측 유지.
4. 완료 기준: 전국 표본(자산유형·시도 다양성 포함) 매칭률 리포트, tier exact+unique만 회귀에 사용.

### Phase 2 — 단독다가구 용도지역 보강 (우선순위 2위, "확정" 아닌 "약한 신호"로 스코프 조정)

Phase 0-B 실측(완전동질 6.4%)에 따라, 이 데이터는 **hard 필터·확정 tier로 쓸 수 없다** — 애초 목표를 "단독다가구 zone_type 결측 해소"에서 **"통합회귀 시 zone_type 더미의 참고용 소프트 신호(다수결 62% 정확도)로 제한 사용"**으로 축소한다.

1. (필요 시) 코드표 확보 후 AL_D155 충북 데이터를 `land_use_zone_registry_pilot`로 적재(파일럿, 충북만, 용도지역 세부만).
2. `built_transactions`(단독다가구, 충북) ↔ 등록부 매칭 — 후보 집합의 최빈 용도지역 + `confidence=최빈값 비율`을 함께 저장(단일 값 강제 아님).
3. 회귀에서는 이 소프트 신호를 **더미 대신 confidence-weighted 방식**으로 실험하거나, 아예 회귀 변수로는 보류하고 UI 참고 정보로만 노출하는 두 옵션을 파일럿에서 비교.
4. 완료 기준: 충북 단독다가구 표본에 대해 (a) 소프트 신호 포함 vs (b) 미포함 CV-MAPE 비교 — **개선이 없으면 이 트랙은 보류로 재분류**.
5. 전국 확장은 Phase 2 결과로 판단(현재는 충북 데이터만 보유, 용량·비용 재평가 필요).

### Phase 3 — 건축물대장 구조 (장기, 기존 로드맵 그대로)
